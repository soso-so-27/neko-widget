# 公式・お題まどの更新手順

2026-09-13。対象は既存TestFlight向けpreviewの「どこかの猫」と「おひるね」。同じまどの写真追加・期限更新にはアプリのビルドやTestFlight再配布は不要。新しい種類のまどをアプリへ追加する場合は別の開発になる。

## 利用者に届ける体験

- 全受信者に同じ掲載を配る。初期の供給目標は週3枚、1回1枚。これは内部運用の目安で、定時配信の対外的な約束ではない。まず今回の1枚で実際の追加を通し、頻度を確約する前に1週間分の候補を確保する。
- 「どこかの猫」は日常のいろいろな姿。「おひるね」は眠る姿。同じ写真が両方に合う場合は1つの原本・ID・初回掲載日を使い、各まどでの掲載履歴を保持する。
- 写真が主役。ひとことは任意の短文、説明や更新状態を写真上に増やさない。AI画像は提供元に「AI生成」を残し、実在の投稿者や撮影日を作らない。
- Widgetは最新の取得済み写真を表示し、開くとそのまど・その写真へ移動する。常に別写真が出るランダム抽選や投稿義務を追加しない。最近の掲載は既存のまど詳細で振り返れる。
- 配信サーバーへの掲載とiPhoneへの反映は別。現行Widgetは次の取得を1時間後に要求するが、実際の時刻はOSが調整する。アプリのまど詳細で更新確認もできる。Appleの[Widget更新方針](https://developer.apple.com/jp/documentation/widgetkit/keeping-a-widget-up-to-date/)に従い、毎時必着とは説明しない。

## 写真の供給・掲載判断

1. 原本、生成プロンプトまたは提供許可の記録、公開用の名前・credit・ひとことをリポジトリ外へ保存する。私的なまどの画像やユーザーのスクリーンショットを素材に転用しない。
2. 目視で猫の自然さ、写真の向き、中央の正方形で顔が残ること、お題との一致を確認する。前回と似すぎる写真が続くときは別の構図を選ぶ。画質を上げるために原本を反復圧縮しない。
3. 既存 `NekoWidget/official-window-tools/build_catalog.py` で追加分だけを生成する。元のmetadataを除去した最大2048pxのJPEGとcatalogになる。`publicationApproved` は担当者の確認結果であり、ツールによる同意の自動判定ではない。
4. 公開する写真のID・初回掲載日時は固定する。既存写真の期限延長を新着として扱わない。猫の個体識別研究やサポート会員制度は前提にしない。

## 更新を準備する

作業ディレクトリは `OfficialWindowService`。出力先の親だけ先に用意し、出力先自体は未作成にする。`--previous` は**直前に実際に配備した**bundleを指定する。写真の追加は既存publisherの出力ディレクトリを絶対パスで渡す。

```json
{
  "schemaVersion": 1,
  "channels": [
    {"channelID": "nap-cats", "addAssets": "C:/official-private/new-nap"}
  ]
}
```

```powershell
node tools/prepare_update.mjs --previous C:/official-review/last/bundle --plan C:/official-private/update.json --output C:/official-review/next
```

全まどを引き継いで新しいbundleを作る。指定しなかったまども消さない。未知のまど追加は拒否する。既存JPEGのbytes、ID、掲載日は維持される。

- 初回だけ、掲載履歴のない旧bundleを確認したうえで `"bootstrapHistory": true` をplanに追加する。2回目以降は削除する。履歴の紛失を初回扱いで回避しない。
- 写真追加がない更新は `{"schemaVersion":1,"channels":[]}`。catalogの期限だけを最大48時間更新し、写真の期限や掲載日は変更しない。
- 写真の継続掲載は、許可範囲を確認して対象まどの `renewPhotos: [{"id":"既存id","expiresAt":"UTC秒精度日時"}]` に明示する。失効済み写真の復活・初回掲載から14日を超える延長は拒否する。
- 対象写真の取り下げは `withdraw: ["既存id"]`。対象まどの休止は `paused: true`。休止は他の操作と併用しない。
- 取り下げ済みを含むID/hashの履歴を `bundle/update-record.json` に残す。同じ画像を別IDで新着に見せる追加も拒否する。履歴・原本・planは公開assetsに入らない。

## 配信前と配信後

1. `update-record.json` の追加・取り下げ・期限、各まどの件数と最新写真を確認する。ゼロ枚や停止が意図どおりか確認する。実行失敗した出力は配備しない。
2. 直前の公開catalogと `--previous` が一致することを確認する。別担当の更新があれば最新bundleから作り直す。配備操作は同時に複数人で行わない。
3. `npm ci --no-audit --no-fund` 済みの環境で、固定Wranglerのdry-runを通す。

```powershell
$env:WRANGLER_SEND_METRICS='false'
node node_modules/wrangler/bin/wrangler.js deploy --dry-run --config C:/official-review/next/bundle/wrangler.jsonc --outdir C:/official-review/next/dry-run
```

4. 同じ候補を、同じコマンドから `--dry-run` と `--outdir` を外して配備する。既存previewの許可範囲内で行い、別アカウント・別サービスへ変更しない。
5. 公開catalogが候補と一致すること、掲載JPEGが200かつhash一致、取り下げたURLが取得不能であることを確認し、Worker versionと時刻を記録する。通常の写真更新でApple画面を確認しない。
6. 写真を戻す場合も、古いWorker版をそのままrollbackしない。アプリは古い生成時刻を拒否する。現在版を基点に新しい日時で訂正版を作り、取り下げ写真の無断復活を避ける。

## 更新がない日・期限・取り下げ

新着写真の供給頻度と、配信データの有効性の保守は別。catalogは48時間、写真は初回掲載から最大14日という現行境界を保つ。catalogだけ更新しても写真の期限は延びない。

`maintenanceDueAt` は24時間以内、または最も早い写真の期限の6時間前の早い方。担当者がその時刻までに次の更新・補充・停止を判断する。期限間近なら現在時刻になる。新着がない日は許可期間内の掲載を保ち、同じ写真を新着と宣伝しない。

配信が失敗した場合は前の配備を残す。アプリは有効なキャッシュを表示するが、期限を超えた写真を表示し続けたり別のまどの写真で埋めたりしない。停止・取り下げを端末が取得すると該当写真を消す。オフラインの端末への即時回収や保存済みコピーの削除は約束できない。

今回のツールはローカル準備だけで、定時実行やバックグラウンド保守を開始しない。運用の担当者は掲載可否・期限を判断し、Codexはこのタスクを実行中に候補生成・検証・配備を担当する。常時稼働する自動配信や投稿受付の完成とは分けて記録する。

## 必要な検証

`npm test` でWorker・bundle・更新履歴をまとめて確認する。アプリコードに変更がなければiOS全体CIを起動しない。新規写真の実機への反映時刻は、HTTPやSimulatorの成功で代用せず通常利用時の確認に残す。
