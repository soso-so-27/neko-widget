# 黒猫のまど：毎日1枚をループする

最初は所有者が確認した10枚を `001.jpg` → `010.jpg` → `001.jpg` の順に繰り返します。切り替えは日本時間0時です。開始日と並びは1つの設定ファイルにまとめます。毎日の編集、cron、D1、期限延長のための定期配備は不要です。このツールはローカル候補だけを作り、アップロード・配備・有効化はしません。

表示クレジットは **ねこのまど（AI で作った画像）** に固定します。生成候補は既存の `neko-widget-official-cats-preview` 用です。本番への切り替えやアカウント・bindingの変更は行いません。Widgetの更新をJST0時に要求しますが、iOSが新しい画像を表示する正確な時刻は保証しません。

## 最初の10枚

承認した公開用JPEGを `001.jpg`〜`010.jpg` として専用フォルダーへ置きます。各4MiB以下、縦横2048px以下、見やすさの目安は正方形1536〜2048pxです。EXIF・コメント・サムネイルを除去したJPEGが必要です。PNGの変換やメタデータ除去は、このツールの前にローカルで行います。

フォルダーには設定に記載したJPEGだけを置きます。未知ファイル、サブフォルダー、リンク、同じJPEGを複数枠へ入れることは拒否します。入力・出力・前回候補は絶対ローカルパスを使い、UNC共有とリンクを含むパスは拒否します。新しい出力先の親フォルダーは先に用意します。

設定ファイルは画像フォルダーの外に置きます。以下の日付は書式例です。実際には所有者が確認した開始日を使います。

```json
{
  "schemaVersion": 1,
  "action": "create",
  "startDate": "2026-12-01",
  "credit": "ねこのまど（AI で作った画像）",
  "order": ["001.jpg", "002.jpg", "003.jpg", "004.jpg", "005.jpg", "006.jpg", "007.jpg", "008.jpg", "009.jpg", "010.jpg"]
}
```

`OfficialWindowService` で実行します。素材・順番・日付の公開許可を得てから `--publication-approved` を付けます。画像を渡すだけでは公開許可になりません。

```powershell
node tools/prepare_black_cat_days.mjs --loop-config "C:\black-cat\loop-config.json" --input "C:\black-cat\reviewed-jpegs" --output "C:\black-cat\candidate-001" --publication-approved
```

`order` が並びの正本です。名前で勝手に並べ直しません。開始日0時に先頭を選び、10日後に先頭へ戻ります。開始前は配信しません。1周の枚数は1〜60枚です。出力内の `loop-config.json` は設定の控え、`schedule-review.json` は元ファイル名と次の2周の掲載日を確認するためのものです。どちらも公開する `assets` の外にあり、内部assetには元ファイル名・元パスを入れません。

## 末尾への追加と公開時のリセット

追加50枚は所有者が確認した後に `011.jpg`〜`060.jpg` として扱います。確認前に自動追加しません。入力フォルダーには新しい並びの全画像を用意します。設定を次のように変更して、別の新しい出力先へ準備します。

- **末尾追加**：`action` を `append`、`startDate` を追加を有効にする将来日、`previousBundle` を最後に承認・配備した候補の絶対パスにします。`order` は以前の並びをそのまま先頭に残し、新画像だけ末尾へ足します。既存画像のhash・順番が変わると拒否します。010の次は011、追加分の最後から001へ進みます。周回途中でも001へ飛びません。
- **公開開始時の001リセット**：`action` を `reset`、`startDate` を公開開始日、`order` を公開時の並びにし、`previousBundle` を指定します。指定日にだけ並びの先頭へ戻ります。それまでは従来のループが続きます。Swift側のカウンターや別の開始日設定はありません。通常追加に混ぜて画像を削除・並べ替えしません。

例えば追加設定には `"previousBundle": "C:\\black-cat\\candidate-001"` を加えます。前回の設定にまだ未来の追加・リセットがある場合は、それより後の日を指定します。古い承認設定を黙って上書きしません。

**追加・リセットは指定日のJST0時より前に準備・配備してください。** 準備時に過去/当日の切り替えを指定すると拒否します。候補作成後に配備が遅れて境界を過ぎた場合も、その候補を配備せず、新しい将来日で作り直します。同日同時刻のcatalogを別の画像へ差し替えると、端末の古い版を拒否する仕組みと衝突するためです。公開開始日を設定すること自体は、本番配備の許可ではありません。

## 配備前の確認と配信の境界

1. `schedule-review.json` と元画像を照合し、日付・並び・クレジット・追加/リセット前後を確認します。ツールは黒猫らしさ、権利、見た目の類似を判定しません。
2. `previousBundle` が現在配備中の候補と一致し、切り替え日がまだ未来であることを確認します。古い候補から準備したりロールバックすると、順序を戻す原因になります。
3. 所有者が候補と対象を確認した後、既存のstaging手順で生成物のソース・設定・assetを一緒に配備します。

Workerはサーバー時刻で今日の1枚のcatalogを作ります。catalogと画像の表示期限は次のJST0時です。同じJPEGが次の周回に出ても、写真IDと掲載日はその日用になります。今日以外のJPEG・内部設定への直接GET/HEADを拒否し、画像の読み込み中に0時を跨いだ場合も応答を止めます。端末が圏外でも昨日の期限を延ばしません。

loopの内部形式は `schemaVersion: 3`。最大64設定・画像pool最大600枚・1周最大60枚で、上限を超えたら停止し、黙って古い設定を捨てません。日数による配信終了ではありません。

## 読み取り監視

ループ配備後は `tools/check_black_cat_loop.mjs --current <current.json絶対パス> --receipt <同じruntime内のlast-check.json絶対パス>` を使います。currentは `schemaVersion: 2`、`mode: "loop"`、`currentBundle`、`workerVersion` を保持します。配備したソースと同じ版のcheckoutで実行してください。

当日のcatalog/JPEG・JST期限・内部/非当日経路・記録したWorker版を照合し、最小のlast-checkだけ保存します。pendingがあれば止まり、配備や期限延長は行いません。同じ正常状態と同じ失敗は繰り返し通知しません。既存の有限予定用監視は互換ではないため、配備後の確認と正本pointerの切替に合わせて呼び出し先も変更します。監視の時刻や通知先は変更する必要がありません。

## 互換用の有限日程

従来の `--start-date YYYY-MM-DD --credit <文字列>` は、画像をファイル名順に1日ずつ割り当てるschema 2の有限日程として維持します。枚数分の日数で配信が終了し、当日と過去6日分をcatalogに含めます。schema 1の複数チャンネル日程も従来どおりです。どちらもループへ暗黙に切り替わりません。新規の黒猫ループには上記の `--loop-config` を使ってください。
