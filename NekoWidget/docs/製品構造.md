# 製品構造

作成：2026-08-21
**機能を足すか迷ったとき、まずここを見る。**

画面上の置き場所と言葉は **[情報設計.md](情報設計.md)** を正本とする。

---

## 1. 製品はふたつの流れでできている

```
【過去の流れ】　発掘・蓄積・差別化
　既にある写真　→　窓に出る　→　肉球　→　溜まる　→　本

【現在の流れ】　即時・相互性・課金
　いま撮る　　　→　家族の窓へ届く　→　送り返される　→　課金
```

**どちらか一方では弱い。**

| | 強み | 弱み |
|---|---|---|
| 過去だけ | **誰もやっていない**（Appleは壁紙、Locketは今だけ） | **社会的機構がゼロ。** そして燃料（写真）が枯れる |
| 現在だけ | **実証済み**（Locket 80M DL）。課金理由が明確 | Locketと同じ土俵。過去の資産を使えない |
| **両方** | **Locketにない過去の深さ ＋ Locketが証明した即時性** | 配分の設計が必要 |

## 2. ★ 燃料の枯渇問題（この議論での最大の発見）

```
見るのが楽になる　→　撮る動機が減る　→　カメラロールが増えない　→　井戸が枯れる
```

**製品が自分の燃料を消費して、補充しない。**

5年後に撮影が減っていたら、「忘れていた写真」は尽きる。同じ写真が回るだけになる。

**現在の流れは、この構造問題への答えでもある。** 撮る理由（家族に届く）を製品の中に作る。

### ただし「促し」と「報酬」は別物

| | 判定 |
|---|---|
| **「今日は撮っていません」と催促する** | **✕ 手間の押し付け** |
| **撮ったものが即座に家族の窓に届く** | **○ 動機のある行為** |

**促さない。報酬を置く。**

## 3. 各機能がどこに属するか

| 機能 | 流れ | 状態 |
|---|---|---|
| **窓（ウィジェット）** | **両方の表示面** | 実装済み |
| 肉球 | 過去 | 実装済み |
| **本・物販** | **過去の出口** | **未実装 ← 最大の穴** |
| 自動アルバム | 過去（並行する枝） | 半分 |
| **共有** | **現在** | 配管のみ。体験は未実装 |
| 撮って送る（共有シート） | 現在 | 未着手 |
| 猫の写真を撮るのを促す | — | **作らない**（促しは手間） |

### 流れのつながり

```
送る　　　　　　→　自動的に「好き」に入る　（送るのは強い肯定なので）
肉球　　　　　　→　「好き」に入る
相手から届く　　→　自分の本には入らない　（別ストア。既に決定済み）
```

**一方向。** 肉球は「本の原稿」の意味のまま。送信は肉球より強い行為として、同じ箱に入る。

## 4. 最大の不整合：出口がない

```
窓　→　肉球　→　溜まる　→　？
　　　　　　　　　　　　　　↑ 空
```

**肉球を押した先に、写真を見返し、必要な分をまとめる出口が必要。**

**入力と表示の面を3つ作って、出口を1つも作っていない。**

### 出口が見える状態は、今すぐ作れる

| 手 | コスト | 効果 |
|---|---|---|
| **「好き」の一覧から写真を選んでまとめる** | **小** | **枚数が増えても、必要な写真だけを出口へ送れる** |
| 単品プリント（1枚から作れる） | 中（手動発送でよい） | 即座に出口になる |
| 書き出し（画像・動画） | 中 | 無料で人に見せられる形 |
| 年次まとめ | 1年待つ | — |

**一番上を先に入れると、共有やアルバムの意味も変わる。** 溜まる先がある状態で作るのと、無い状態で作るのとでは、機能の意味が違う。

---

## 5. 解決した衝突

| 衝突 | 解決 |
|---|---|
| 肉球の意味が拡散する | **相手の肉球を別ストアに。** 肉球は「本の原稿」1つの意味を保つ |
| アプリ内カメラは標準カメラに勝てない（猫は待たない） | **アプリ内カメラを作らない。共有シート（Share Extension）で送る** |
| 写真アプリでキュレーションさせるのは核と矛盾 | **作らせない。既に持っている人に検知して提案するだけ** |
| 多頭で年齢アルバムが破綻する | **誕生日が同じなら共通。違うなら迎えた日で時期分割。個体識別は不要** |

### 新しく確立した原則

> **設定を1回お願いするのはいい。キュレーションをお願いするのは駄目。**

壁紙の案内は前者（アルバムを作り続けるのは我々）。写真アプリでアルバムを作らせるのは後者。

> **促さない。報酬を置く。**

## 6. 未解決の衝突

| 衝突 | 検討中 |
|---|---|
| **窓の意味が曖昧になる** | 「3年前の今日」と「さっき撮った」が同じ枠に出る。**「いつ変わるか分からない」問題の再来**。→ 送られたものは一定時間優先し、「さっき」と分かる表示に |
| **過去の発掘が脇に追いやられる** | 即時性のほうが刺激が強い。**差別化の核が薄まる可能性**。配分の設計が必要 |
| アルバムを作り込むほど「開かせない」が薄まる | 用途が違う（日常 vs 見たいとき）ので致命傷ではないが、比重に注意 |
| 共有で製品の性質が変わる | 「静かなローカルの道具」から「サービス」へ。サーバー・運用・プライバシー申告 |

詳細はすべて **[共有設計.md](共有設計.md)** に移した。要点だけ：

| | |
|---|---|
| 採用 | **D案。** 長辺2048px／追記のみ／受領後7日・未受領30日／E2E |
| 見積 | 月$9〜11（1万人・1日1枚） |
| **不採用** | **B（オリジナル無期限）。** 鍵を失うと復元不可なのに、バックアップに見える |

## 8. 優先順位

```
1　オンボーディング　　　　　　　　　配れる状態を作る（決定済み）
2　「これ好き」から写真をまとめる　　　肉球に目的を与える
3　共有　＋　撮って送る　　　　　　　現在の流れ。社会的機構の穴を埋める
4　アルバム（bbox分類まで）　　　　　既に半分できている
5　単品プリントか書き出し　　　　　　出口を実体化する
─────────────────────────
作らない　撮影の促し（催促）
後回し　　個体識別、専用モデル、フォロー、公開SNS
```

**3を作る前に、7のサーバー設計を確定させる。**

## 9. 検証の状態（正直に）

| | 状態 |
|---|---|
| **他人が使ったことがあるか** | **ゼロ人** |
| 本人が使って嬉しいか | **確認済み**（「既に嬉しい」「妻に見せたくなる」） |
| 即時共有に価値があるか | **未検証**（観察1回のみ） |
| 肉球が押されるか | **未検証**（計測は撤回） |
| 本が買われるか | **未検証**（本が存在しない） |

**方針として、オンボーディング・共有・アルバム・入力の仕組みが揃うまで、他のテストユーザーには出さない。** それまでは本人＋古いiPhoneの2台で検証する。共有は2台必要なので、開発上も自然な順番。
