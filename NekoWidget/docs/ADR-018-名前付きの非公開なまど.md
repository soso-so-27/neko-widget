# ADR-018：共有先は家族限定ではなく、名前付きの非公開な「まど」にする

> **2026-08-26追記:** Share Extensionのactiveまど限定方針は後続実装で更新した。現在は、Host appが発行した期限内かつ現存する複数まどの候補を表示し、利用者が明示選択する。選択IDはHost appで再検証し、失効時や曖昧な旧形式では別まどへ自動fallbackしない。以下のactiveまど限定記述は当時の安全境界を残す履歴である。
>
> **2026-08-26 通知境界の追記:** 通知登録もactiveまど1件だけの方式から更新する。通知を受け取れる設定と資格を持つ接続済みの各まどを、同じiPhoneから独立して登録し、各通知には端末内でだけ照合する対象まど・写真を含める。非選択中のまどに通知が届いただけでは、そのまどをbackground同期せず、選択中のまど、表示中の写真、Widget cacheを変更しない。利用者が通知をタップしたときだけ、対象と一意に一致するまどを選択して認証済み同期を行い、対象写真を開く。一致しなければ別のまどへfallbackしない。非選択中のまどを通知だけでbackground同期し、そのまどのWidgetまで更新する機能は後続課題である。

## 提案

製品上の共有単位を「家族」という関係ではなく、利用者が名前を付ける招待制の非公開な「まど」とする。友人、恋人、離れて暮らす人も利用できる一方、初期版の能力は次に限定する。

- 1台につき最大20の独立したまど
- 作成者と、信頼できる招待相手1人の合計2人
- 1人につき、相手の確認を受けたiPhoneを最大4台
- 招待制、非公開、検索・公開feed・followなし
- まど名は変更可能な表示情報であり、spaceの識別子や暗号鍵に使わない

安全性は「家族」という呼称ではなく、人数、明示招待、二者確認、端末資格、E2E暗号化、通報、block、共有解除で守る。

## 用語

| 表示 | 意味 |
|---|---|
| `ねこのプロフィール` | 名前、日付、利用者が明示した写真を猫ごとに確認する場所 |
| `このiPhoneの猫写真` | このiPhoneから読める写真のうち、端末内で見つけた猫写真を使うWidget写真源 |
| `写真アプリの「うちの子」アルバム` | 既存利用者との互換性のため当面維持する、Photosへ作る出力アルバムの固有名 |
| `しずくのまど`など | 利用者が名前を付け、招待相手と一枚を届け合う共有空間 |
| `しずくのまどに届いた一枚`など | そのまどの「届いた写真」に加わる一枚。まど自体を送信者のように扱わない |
| `ウィジェット` | 選択した写真源またはまどを覗く表示枠 |

「箱」は保存・バックアップを連想させるため、共有先の製品語には使わない。`うちの子`を猫、プロフィール、選別結果、写真源の総称として単独表示すると何を指すか分からないため使わない。既存のPhotos出力アルバムを案内するときだけ、`写真アプリの「うちの子」アルバム`と対象を明記する。Widget写真源は`このiPhoneの猫写真`、猫ごとの設定は`ねこのプロフィール`と表示する。

共有写真の出所は招待相手だが、利用者が「届いた写真」を見つける場所は名前付きのまどである。通常表示は`〈まど名〉に届いた一枚`とし、まど自体を人物のように扱う`〈まど名〉から届いた一枚`は使わない。送信者を説明する必要がある画面だけ`招待した相手から届いた写真`と書く。

## 段階

1. **完了：** 表示語だけを整理し、「家族から」を「〈まど名〉に届いた一枚」、「うちの子（写真源）」を「このiPhoneの猫写真」、「うちの子（猫ごとの設定）」を「ねこのプロフィール」へ変える。
2. **完了：** 既存の単一spaceへ変更可能なまど名を追加する。既存利用者はペアリングを解除せず、初期表示名から任意に改名できる。最初は名前を端末ローカルの表示情報として保存する。
3. **完了：** まど名を参加端末間で同期する。作成者だけを更新主体とし、room keyから写真とは別domainで導出した鍵による暗号文と作成者署名だけをserverへ置く。
4. **実装済み・実機検証前：** 資格情報、履歴、Widget cache、deep link、Share Extension届け先をローカルまどID単位へ分離し、複数のまどを追加する。
5. **一部実装：** 相手の確認を伴う追加端末は、既存端末を失効させず同じ参加者へ最大4台まで追加する。通知を受け取れる接続済みの各まどへのalert登録と、通知タップ後の対象まど選択・同期を実装する。3人以上の参加、端末一覧からの個別失効、非activeまどの通知起点バックグラウンド同期は未実装。

## 段階4の実装契約

複数まどは、画面に切替UIを足すだけでは実装しない。次の境界を同じ変更単位で導入し、1つのまどのデータが別のまどへfallbackしない自動テストを通してから有効にする。

- `WindowID`: 表示名や招待コードとは別の、変更されない不透明な識別子。改名で変えず、ログへ生値を出さない。
- `WindowCatalog`: このiPhoneが参加できるまどと役割を列挙する。現在の単一まどを暗黙の既定値として別のまどへ流用しない。
- `WindowContext`: `WindowID`を必須引数として、資格情報、暗号鍵、送信待ち、受信cursor、履歴、通報・block・解除状態を解決する。process-wide singletonから暗黙に現在のまどを読む実装を残さない。
- per-window隔離: Keychain item、App Group上のstate、暗号化写真、Widget cache、一時handoffを`WindowID`単位へ分ける。消去、容量上限、保持期間、再試行も各まどだけを対象にする。
- Widget: 設定用`AppEntity`は表示名ではなく`WindowID`を保持し、timeline、cache、deep linkを同じIDへ束縛する。資格がない、解除済み、不明なIDでは空表示へfail closedし、個人写真や別のまどへfallbackしない。
- Share Extension: `WindowCatalog`の検証済みsnapshotから、ホストが現在処理できるactiveまどだけを届け先として表示し、handoffへ`WindowID`を束縛する。不明なIDや複数候補では送信しない。非activeまどを明示スコープのまま即時promotionできるまでは、選べるように見せない。
- deep link: `WindowID`を含め、現在の資格と照合してから開く。表示名をrouteへ使わない。
- migration: 現在の単一spaceへ一度だけ`WindowID`を割り当て、資格情報、履歴、Widget cacheを原子的に移す。途中失敗時に旧stateと新stateを同時利用しない。

現在の実装候補は、既存の単一`sharing/`をcrash-resumableに1つ目のローカルまどへ移し、以後はまどごとのApp Group subtree、資格情報、Widget設定、cache、deep link、共有シート届け先を使う。まどは複数持てるが各まどは引き続き2人だけで、本人の追加端末は相手の確認を必要とする。APNs tokenは物理iPhoneで共通だが、通知を受け取れる接続済みの各まどは、それぞれの資格で独立したdevice subscriptionを登録する。あるまどの登録更新で別のまどの有効な登録を置き換えない。

Share Extensionの短期handoffは、まどごとのauthorityを分離するためApp Group内の共通v2 directoryへ置く。ただしadmissionは安定したローカルまどIDとpairing bindingへ必ず束縛し、captureの上限・取消・promotionはadmission単位とする。既存の単一まどhandoff directoryはライフサイクルlock中に1回だけ原子的に移動し、旧・新の両方または複数の旧directoryが存在する場合はmergeせずfail closedにする。現段階の共有シートはactiveまど1つだけを表示し、別のまどへ届ける場合は先にホストアプリでそのまどを開く。

追加した本人iPhoneは独自のdevice署名鍵を持つが、作成者名の正本署名鍵ではない。このため作成者の追加iPhoneではまど名を閲覧専用とし、「最初のiPhoneで変更」と案内する。端末ごとの個別失効と、作成者権限を安全に別端末へ委譲するceremonyは後続課題とする。

通常の前面操作と手動更新は選択中のまどを同期する。APNsのalertは、通知を受け取れる設定と資格を持つ接続済みの各まどへ登録する。通知本文はまど名、相手名、写真、内部識別子を含まない一般文とし、対象を示す不透明な値は端末内の照合とタップ後のroutingだけに使い、画面や通常の診断へ表示しない。

非選択中のまどにremote notificationが届いても、background callbackはそのまどの同期を開始せず、選択中のまどを切り替えず、いずれのWidget cacheも書き換えない。利用者が通知をタップしたときは、保持した対象全体を検証し、端末内で一意に一致するまどを先に選択してから、そのまどの資格で同期する。対象写真まで一意に解決できた場合だけ該当画面を開き、解決できなければ現在のまどや別の写真へfallbackしない。選択中のまどに対する既存のbest-effort background同期は維持するが、通知は同期の正本・端末到着・Widget更新の証明ではない。非選択中のまどを明示スコープでbackground同期し、そのまどを選んだWidgetまで更新する機能は後続課題とする。

## 互換性

既存の内部識別子`personal-library`、`family-window`とdeep link `nekowidget://family-window`は互換入口として残す。表示名をidentifierへ使うと改名だけでWidgetや履歴が切れるため、既存spaceに安定したローカルIDを対応付ける。

全まどalert登録から旧v2へrollbackする場合、旧client／旧serverのactiveまど1件だけを登録する契約を安全側の互換境界として維持する。旧v2は非選択中のまどへ通知を拡張せず、同じ物理tokenの旧bindingを従来どおり選択中の1件へ収束させる。rollback中は受け取れる通知の範囲が狭くなるが、対象のない旧通知から別のまどを推測したり、非選択中のまどを同期したりしない。利用者には内部version、token、まど・写真の不透明な識別子を表示せず、通知には一般文だけを、アプリ内では通常のまど名だけを見せる。

段階Aでは用語整理と単一まどの改名だけを実装する。まど名はPairingStateへ混ぜず、pairing identityに結び付けた`sharing/window-presentation.v1.json`へ保存する。改名でPairingStateのCAS、招待、暗号鍵、送信待ち、履歴、Widget/Deep Linkの安定IDは変えない。共有解除・block・再インストール時は既存の`sharing/`一括消去で名前も削除する。

段階Bでは写真Moment/change feed/R2とは別の単一レコードAPIを使う。serverは平文名を受け取らず、作成者だけが署名付きPUTを行い、招待相手はGETと作成者署名・AEADの検証後に表示へ反映する。暗号化前の名前領域は64 UTF-8 byteへpaddingして暗号文長から名前長を推測できないようにする。順序番号と暗号文hashのrollback floor、曖昧なPUTを同じbyte列で再送するローカルpending stateは`sharing/window-name-sync.v1.json`に保存し、Build 32の`window-presentation.v1.json`とは分離する。

Build 31/32は新APIを呼ばず、既存の写真・鍵・pairing responseも変わらない。後続Buildの作成者は既存ローカル名を初回だけ暗号化してseedし、招待相手は検証済み作成者名が届くまでローカル名または中立名を維持する。名前同期の障害は写真の送受信、ACK、cursor、履歴を止めない。server側の写真runtimeと名前runtimeは独立したexact flagを持つが、両方を安全に外部OFFへ切り替えて同じdeploymentを検証するrepository内の実停止経路は未実装である。共有解除・block・再インストールではローカル同期stateとserver暗号文を削除する。複数まどや3人以上へは同時に広げない。

Build 34の本人所有2台による内部TestFlightでは、既存ペアリングを維持したまま作成者のまど名が招待相手へ暗号化同期されることを確認した。Build 35候補は段階4へ進まず、作成／参加を最初に分け、現在の役割と次の操作、変化がない場合を含む手動確認結果、機種変更と共有解除の案内を明確にする。内部識別子、暗号鍵、server protocol、単一まど・2人という能力境界は変えない。
