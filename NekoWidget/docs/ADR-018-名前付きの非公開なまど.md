# ADR-018：共有先は家族限定ではなく、名前付きの非公開な「まど」にする

日付: 2026-08-23
状態: 採用・段階1〜3実装済み、段階4以降未着手
関連: [ADR-009](ADR-009-ローカルアルバムと招待制共有.md)、[ADR-017](ADR-017-家族共有v1とmoderation境界.md)、[情報設計](情報設計.md)

## 提案

製品上の共有単位を「家族」という関係ではなく、利用者が名前を付ける招待制の非公開な「まど」とする。友人、恋人、離れて暮らす人も利用できる一方、初期版の能力は次に限定する。

- 1人につき1つのまど
- 作成者と、信頼できる招待相手1人の合計2人
- 招待制、非公開、検索・公開feed・followなし
- まど名は変更可能な表示情報であり、spaceの識別子や暗号鍵に使わない

安全性は「家族」という呼称ではなく、人数、明示招待、二者確認、端末資格、E2E暗号化、通報、block、共有解除で守る。

## 用語

| 表示 | 意味 |
|---|---|
| `ねこのプロフィール` | 名前、日付、利用者が明示した写真を猫ごとに確認する場所 |
| `このiPhoneの猫写真` | このiPhoneから読める写真のうち、端末内で見つけた猫写真を使うWidget写真源 |
| `写真アプリの「うちの子」アルバム` | 既存利用者との互換性のため当面維持する、Photosへ作る出力アルバムの固有名 |
| `しずくのまど`など | 利用者が名前を付け、招待相手と一枚を届け合う共有空間 |
| `しずくのまどに届いた一枚`など | そのまどの履歴へ届いた写真。まど自体を送信者のように扱わない |
| `ウィジェット` | 選択した写真源またはまどを覗く表示枠 |

「箱」は保存・バックアップを連想させるため、共有先の製品語には使わない。`うちの子`を猫、プロフィール、選別結果、写真源の総称として単独表示すると何を指すか分からないため使わない。既存のPhotos出力アルバムを案内するときだけ、`写真アプリの「うちの子」アルバム`と対象を明記する。Widget写真源は`このiPhoneの猫写真`、猫ごとの設定は`ねこのプロフィール`と表示する。

共有写真の出所は招待相手だが、利用者が履歴を見つける場所は名前付きのまどである。通常表示は`〈まど名〉に届いた一枚`とし、まど自体を人物のように扱う`〈まど名〉から届いた一枚`は使わない。送信者を説明する必要がある画面だけ`招待した相手から届いた写真`と書く。

## 段階

1. **完了：** 表示語だけを整理し、「家族から」を「〈まど名〉に届いた一枚」、「うちの子（写真源）」を「このiPhoneの猫写真」、「うちの子（猫ごとの設定）」を「ねこのプロフィール」へ変える。
2. **完了：** 既存の単一spaceへ変更可能なまど名を追加する。既存利用者はペアリングを解除せず、初期表示名から任意に改名できる。最初は名前を端末ローカルの表示情報として保存する。
3. **完了：** まど名を参加端末間で同期する。作成者だけを更新主体とし、room keyから写真とは別domainで導出した鍵による暗号文と作成者署名だけをserverへ置く。
4. **未着手：** 資格情報、履歴、Widget cache、deep link、Share Extension届け先をspace ID単位へ分離してから、複数のまどを追加する。
5. **未着手：** 鍵更新、招待承認、解除、deliveryを再設計してから、3人以上または1人の複数端末を追加する。

## 段階4の実装契約（未実装）

複数まどは、画面に切替UIを足すだけでは実装しない。次の境界を同じ変更単位で導入し、1つのまどのデータが別のまどへfallbackしない自動テストを通してから有効にする。

- `WindowID`: 表示名や招待コードとは別の、変更されない不透明な識別子。改名で変えず、ログへ生値を出さない。
- `WindowCatalog`: このiPhoneが参加できるまどと役割を列挙する。現在の単一まどを暗黙の既定値として別のまどへ流用しない。
- `WindowContext`: `WindowID`を必須引数として、資格情報、暗号鍵、送信待ち、受信cursor、履歴、通報・block・解除状態を解決する。process-wide singletonから暗黙に現在のまどを読む実装を残さない。
- per-window隔離: Keychain item、App Group上のstate、暗号化写真、Widget cache、一時handoffを`WindowID`単位へ分ける。消去、容量上限、保持期間、再試行も各まどだけを対象にする。
- Widget: 設定用`AppEntity`は表示名ではなく`WindowID`を保持し、timeline、cache、deep linkを同じIDへ束縛する。資格がない、解除済み、不明なIDでは空表示へfail closedし、個人写真や別のまどへfallbackしない。
- Share Extension: `WindowCatalog`の検証済みsnapshotから届け先を選び、handoffへ`WindowID`を束縛する。候補が1つの間は選択UIを出さず、複数になったときだけ明示選択を出す。不明なIDでは送信しない。
- deep link: `WindowID`を含め、現在の資格と照合してから開く。表示名をrouteへ使わない。
- migration: 現在の単一spaceへ一度だけ`WindowID`を割り当て、資格情報、履歴、Widget cacheを原子的に移す。途中失敗時に旧stateと新stateを同時利用しない。

この契約は将来設計の記録であり、現在の実装は引き続き**名前付きの非公開なまど1つ、作成者と招待相手1人、各1台**に限定する。複数まど、3人以上、1人の複数端末、APNsによる更新はこの段階では有効にしない。

## 互換性

既存の内部識別子`personal-library`、`family-window`とdeep link `nekowidget://family-window`は互換入口として残す。表示名をidentifierへ使うと改名だけでWidgetや履歴が切れるため、既存spaceに安定したローカルIDを対応付ける。

段階Aでは用語整理と単一まどの改名だけを実装する。まど名はPairingStateへ混ぜず、pairing identityに結び付けた`sharing/window-presentation.v1.json`へ保存する。改名でPairingStateのCAS、招待、暗号鍵、送信待ち、履歴、Widget/Deep Linkの安定IDは変えない。共有解除・block・再インストール時は既存の`sharing/`一括消去で名前も削除する。

段階Bでは写真Moment/change feed/R2とは別の単一レコードAPIを使う。serverは平文名を受け取らず、作成者だけが署名付きPUTを行い、招待相手はGETと作成者署名・AEADの検証後に表示へ反映する。暗号化前の名前領域は64 UTF-8 byteへpaddingして暗号文長から名前長を推測できないようにする。順序番号と暗号文hashのrollback floor、曖昧なPUTを同じbyte列で再送するローカルpending stateは`sharing/window-name-sync.v1.json`に保存し、Build 32の`window-presentation.v1.json`とは分離する。

Build 31/32は新APIを呼ばず、既存の写真・鍵・pairing responseも変わらない。後続Buildの作成者は既存ローカル名を初回だけ暗号化してseedし、招待相手は検証済み作成者名が届くまでローカル名または中立名を維持する。名前同期の障害は写真の送受信、ACK、cursor、履歴を止めない。server側は写真runtimeとは独立したexact kill switchを持ち、media-stagingの通常運用では両方ON、緊急OFFでは両方NOとして公開監視で確認する。共有解除・block・再インストールではローカル同期stateとserver暗号文を削除する。複数まどや3人以上へは同時に広げない。

Build 34の本人所有2台による内部TestFlightでは、既存ペアリングを維持したまま作成者のまど名が招待相手へ暗号化同期されることを確認した。Build 35候補は段階4へ進まず、作成／参加を最初に分け、現在の役割と次の操作、変化がない場合を含む手動確認結果、機種変更と共有解除の案内を明確にする。内部識別子、暗号鍵、server protocol、単一まど・2人という能力境界は変えない。
