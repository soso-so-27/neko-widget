# ADR-009：ローカルアルバムを先行し、Widgetの20枚だけを招待相手と共有する

- 状態：承認済み・段階実装待ち
- 日付：2026-08-17
- 対象：1週間計測と分離して開発するローカルアルバム、およびその後の招待制共有

## 背景

本製品で確認できた共有欲求は、「好きにした写真を送る」ことではなく、Widgetに過去の写真が現れた瞬間に「妻にも見せたい」と感じることである。共有後に作るべき状態は、送信者がいまWidgetで巡回させている写真と同じ集合が、招待相手のホーム画面にも静かに現れることである。

肉球は「本の原稿にしたい写真を残す」という意味に固定する。共有対象を選ぶ操作に流用すると、肉球が保存と送信の二つの意味を持つため採用しない。相手が共有写真へ付けた肉球は社会的な反応として相手にも見せるが、個人の本の候補とは保存先と集計を分け、共有集合の選択にも使わない。

共有はサーバー、審査、プライバシー申告を伴う。一方、猫判定済み写真を一覧するアルバムは端末内だけで完結する。このため両者を同じリリース変更にせず、まずローカルアルバムを実装・検証し、その後に共有を実装する。

## 判断1：ローカルアルバムを先に実装する

第1段階では、既存の確定snapshotを使う端末内アルバムだけを実装する。

- 猫と判定された写真を撮影日時順のgridで表示する。
- 「すべて」と「好き」のfilterを設ける。
- 写真をタップすると、既存の写真ブラウザの該当写真を開く。
- 写真、判定結果、好き情報をサーバーへ送らない。
- 現在の1週間計測中は計測端末へインストールせず、計測条件を変えない。

第2段階の共有実装は、ローカルアルバムの受け入れ確認後に開始する。共有のためにアルバムの写真を手動選択させるUIは追加しない。

## 判断2：共有するのは送信者の現在のWidget候補20枚である

共有単位を、送信者の`personal-library` Widget manifestにある現在世代の候補、最大20枚とする。

- 肉球を押した写真だけを共有する方式は採用しない。
- アルバムで選択した写真、写真アプリのお気に入り、直近20枚という別の集合へ置き換えない。
- 送信者側でWidget候補の新しい世代が確定したとき、その同じ最大20枚に対してアプリ本体が既に生成したfamily別Widget派生画像を共有候補にする。
- 受信者の「共有されたねこ」写真源は、その世代、順序、切り替え基準時刻を受け取る。
- 両端末は取得済みの同じ世代を使い、約20分の切り替えを端末内で計算する。20分ごとに画像をアップロードまたは再取得しない。
- WidgetKitの実際の更新時刻はOS裁量なので、両ホーム画面が常に同じ瞬間の1枚を表示することまでは保証しない。同じ取得済み世代、順序、切り替え基準を使い、更新後に同じ集合が巡回することを製品契約とする。

送信するのはWidget用の派生画像だけである。原本、PhotoKitの`localIdentifier`、ファイル名、EXIF、位置情報は送らない。派生画像は[ADR-007](ADR-007-Build8計測修復と最終UX.md)の現行仕様と同じSmall `500×500px / 100KiB以下`、Medium `1050×500px / 200KiB以下`、Large `1050×1100px / 220KiB以下`の3 variantとする。各objectは「Widget用の小さい画像50〜300KB」という目安の上限内であり、50KB未満になったobjectを水増ししない。最大20枚とは写真の件数であり、R2 objectは最大`20枚 × 3 family`になる。全20枚を初回同期する理論上限は暗号化overheadを除き約10.2MiBで、通常の更新はhashが変わったobjectだけを差分転送する。送信元で現在の20枚から外れた写真は、サーバー側でも現行集合から外す。

一つのcanonical previewを送り、受信側で各familyへ再構成する方式は採用しない。既存の猫union、8%余白、Mediumの上寄りcropなどを送信側アプリ本体で確定し、受信側Widget Extensionは該当familyの復号済みJPEGをdecodeして表示するだけにする。これにより、共有導入後もWidget ExtensionでPhotoKit、Vision、crop、blur、resize、JPEG再圧縮を実行しない。

## 判断3：肉球は共有commandにしない

肉球を押す操作は共有の開始、停止、対象追加、対象削除を一切発火しない。

- 自分の写真源で押した肉球は、既存の個人用Likeストアに保存し、自分の本の候補として扱う。
- 相手の共有写真へ押した肉球は、pair単位のreactionストアへ保存し、相手の画面にも表示する。
- pair reactionを自分または相手の個人用Likeストアへ複製しない。
- pair reactionを1週間計測の「自分の好き」へ含めない。
- reactionの有無によって共有する20枚を変更しない。

これは[ADR-004](ADR-004-Widget肉球ボタンとBuild6計測.md)で保留していた「他人の猫」の写真源別action policyを具体化する判断である。timeline entryは写真源とaction policyを明示し、表示側が写真源名から保存先を推測しない。

## 判断4：APNsを使わず、同期は起動時とWidget更新時のbest effortにする

共有にはAPNs、silent push、通知権限、push tokenを導入しない。即時配送は価値の中心ではなく、「過去の写真がゆっくり浮かび上がる」「窓は静か。話しかけてこない」という設計思想を優先する。

同期契機は次の二つに限定し、background timerやserver起点のwakeを追加しない。

1. ユーザーがアプリを開き、共有状態を読み込むとき
2. WidgetKitがtimeline更新の機会を与えたとき

送信側のWidget更新では、App Groupに準備済みでhash検証済みの3 family派生画像とmanifestだけをupload対象にする。Widget Extension内でPhotoKitの原本取得、Vision解析、crop、blur、resize、JPEG再圧縮を行わない。現在世代の3 variantが揃っていなければ不完全な世代をpublishせず、最後に検証済みの共有世代を維持する。受信側はrevisionを条件付き取得し、変化した世代のfamily別objectだけをdownloadする。通信失敗時は最後に検証済みの世代を表示し、次の起動またはWidget更新時に再試行する。

OSはWidgetの20分ごとの実行を保証しないため、相手への反映時刻も保証しない。サーバーは世代の交換場所であり、写真の20分ローテーションを駆動するschedulerにはしない。

APNsを使わないため、共有機能のためのDevice IDは収集しない。疑似匿名のinstallation member IDはUser IDとして申告し、端末識別子へ流用しない。

## 判断5：画像本文は参加端末間で暗号化するが、招待経路の限界を明示する

共有画像とreaction本文には、参加端末だけが保持するroom keyによる認証付き暗号化を採用する。Cloudflare Workers、R2、D1には平文画像とroom keyを保存せず、サービス運営者が保存画像を復号できない構造にする。通信路のTLSはこのcontent encryptionとは別に維持する。

招待linkまたは対面QRへ載せるのは、有効期限付き・一回限りの高entropyな`enrollment secret`だけとする。長期のroom key、画像content key、参加済み端末のprivate keyは絶対に載せない。enrollment secretは可能な限りURL fragmentに置き、当社serverへのHTTP requestや通常のserver logには送らない。serverには招待lookup値、secretのdigest、有効期限、使用済み状態だけを保存する。

Pairingは次の順序で行う。

1. 招待を受けた端末は、installation専用の暗号化key pairを端末内で新規生成し、enrollment secretを知る証明とpublic keyだけをpending enrollmentとして登録する。
2. 両端末は、space、双方のpublic key、pending enrollmentを含む同じcanonical transcriptから短いverification phraseまたはfingerprintを表示する。
3. 招待者は、相手側に表示されたphraseとの一致を対面または別経路で確認し、pending端末を明示的に承認する。phraseの確認前に自動承認しない。
4. 承認後にだけ、招待者端末がroom keyを招待先public keyへwrapし、暗号化されたkey envelopeを渡す。room keyの平文は招待者端末から出さない。
5. 招待先端末がkey envelopeを復号してpairingを完了したら、enrollment secretとpending enrollmentを失効する。

LINE、メール、SMSなどで招待linkを送ると、link全体とenrollment secretは選んだ通信サービスを通過する。その経路の事業者、履歴へアクセスできる者、または転送されたlinkを有効期限内に取得した者は、自分のpublic keyでpending enrollmentを試みたり、正規受信者より先に招待を消費して利用不能にしたりできる。ただし、verification phraseを確認した招待者の明示承認なしにはroom key envelopeを受け取れないため、linkを取得しただけで既存・将来の共有画像を秘密裏に復号できる設計にはしない。

それでもpairingの安全性は、enrollment secretを運ぶ経路の秘匿性と、利用者がverification phraseを正しく照合することの両方に依存する。招待者が攻撃者のphraseを相手のものと誤認して承認した場合、または照合を省略した場合、その攻撃者へroom keyをwrapしてしまい、以後の共有内容を復号され得る。したがって、次のように説明する。

> 共有写真は、確認済みの端末だけが読めるよう端末間で暗号化されます。ねこのまどのサーバーには写真の復号鍵を保存せず、招待リンクにも復号鍵は入れません。ただしリンクには参加手続き用の一回限りの秘密情報が含まれ、LINEなど選んだ送信経路を通ります。リンクは信頼できる相手にだけ送り、参加前に両方の端末に表示される確認フレーズが同じことを確かめてください。より安全に招待する場合は、対面でQRコードを読み取ってください。

この方式を製品上で「エンドツーエンド暗号化」と呼ぶのは、verification phraseを照合してpairingが完了した後の「共有画像の内容とreaction payload」に限定する。招待経路そのものはE2E保護の範囲外であり、「招待経路を含むすべてを当社以外の第三者から秘匿する」「linkが漏れても安全」とは表示しない。確認を省略または誤ると別端末へ鍵を渡し得ることも隠さない。

Serverは運用に必要なmetadata、すなわちpairの存在、member ID、暗号文の件数・size・送信時刻、世代と順序、どのmemberがどのmediaへreactionしたかを知り得る。写真の内容、reactionに将来付加する本文、room keyは知らない。「誰と共有しているかを含め一切のmetadataが見えない」とは主張しない。

### 脅威モデルと対象外

保護する対象は、Cloudflare上の保存内容、pairing完了後に通信する画像本文、推測可能な短い招待codeへの総当たり、盗んだlinkだけによる無確認のroom key取得である。一回限り、短い有効期限、十分なentropy、rate limit、public keyの明示確認、使用後の無効化を必須とする。

端末のロック解除後に端末を操作できる者、侵害された送信経路、受信者が保存した画像、スクリーンショット、画面撮影からは保護できない。相手の端末に保存されたcopyは、送信者が共有解除しても回収できない。この限界を共有開始前とプライバシーポリシーに明記する。

## 判断6：共有鍵はinstallationへ束縛し、復旧accountを作らない

氏名、メール、電話番号、passwordを使う復旧accountは作らない。member identityと鍵はinstallation単位とし、機種変更、アプリ削除・再インストール、installation data消失後に自動復旧しない。新しいinstallationでは新しい鍵とmember IDを発行し、相手から再招待を受ける。

Keychain itemが再インストール後も残る場合があるというOS挙動だけに依存しない。通常のapp containerにinstallation markerを置き、markerがない起動では残存credentialを再利用しない実装契約とする。移行・restoreを含む境界は実機で検証し、「復旧できる場合もある」挙動を製品仕様にしない。

共有を有効にする直前に、次の文言を確認画面へ表示する。

> この共有は、このiPhoneに保存する鍵で保護されます。機種変更、アプリの削除・再インストールをすると共有を引き継げません。相手からもう一度招待してもらう必要があります。
>
> 共有解除後も、相手が端末へ保存した写真やスクリーンショットは削除できません。

同意後だけ招待作成または参加を進める。設定画面にも同じ制約を短く常設する。

## Server data model

D1には内容を最小限にした次のmetadataだけを置く。

- `spaces`：非公開pairと現在revision
- `members`：space内だけで意味を持つinstallation member ID、public key、承認時刻、role、失効時刻
- `invites`：一回限りの招待lookup、enrollment secret digest、有効期限、使用時刻、pending enrollment状態。room keyは保存しない
- `key_envelopes`：承認済みmemberのpublic key宛てにwrapしたroom key。平文room keyは保存しない
- `generations`：送信者Widget候補の世代、件数、順序基準、切り替え基準時刻
- `media`：写真単位の暗号化object group、世代内順序、作成時刻
- `variants`：mediaごとのSmall / Medium / Large、暗号化object key、暗号文size、hash
- `reactions`：space、media、反応したmember、暗号化payload、更新時刻
- `deletion_jobs`：R2削除失敗時の再試行状態

R2 bucketはprivateとし、公開URLを作らない。Workerはspaceのcredentialを検証した後だけ短時間のobject accessを仲介する。request body、招待link、IP addressをapplication logへ保存せず、運用logは件数、遅延、失敗率の集計に限定する。

## 保持、削除、privacy境界

サーバーが保持するのは、一つの共有写真源につき最新20枚まで、かつ送信後30日以内とする。どちらか早い条件で対象外になった暗号文を削除する。

- 新しい世代のpublishは、全objectのuploadとhash検証後にD1の現行revisionを原子的に切り替える。
- 新しい現行集合にない旧objectは直ちに削除対象へ入れ、失敗時は`deletion_jobs`で再試行する。
- 共有解除では最初にmember credentialとread権限を即時失効し、続けてR2 objectとD1のlive dataを削除する。
- unlink処理中でも失効済みcredentialからは取得できない。
- 送信端末を失ってunlinkできない場合にも無期限保持しないよう、30日のhard TTLを維持する。
- 相手が既に端末へ保存したcopyやスクリーンショットは削除できない。

共有を導入するbuildでは、App Storeの「データを収集しません」という現行申告を維持しない。暗号文であっても端末外へ送信して保持するため、保守的に次をApp Functionality目的、User linked、Trackingなしとして申告する。

- Photos or Videos：Widget用の縮小・暗号化画像
- User ID：疑似匿名のspace/member ID
- Product Interaction：相手への肉球reaction

APNs token、広告ID、連絡先、氏名、メール、位置情報、原本は収集しない。Device IDは申告対象に追加しない。Cloudflareを処理委託先としてプライバシーポリシーへ記載し、共有するdata、利用目的、暗号化、最新20枚かつ30日の保持、unlink時の削除、相手のcopyを回収できないこと、広告・tracking・販売・AI学習へ使わないことを説明する。

共有を実装していないbuildでは、共有用の申告を先行変更しない。共有機能を含むbuildを審査へ出す前に、App Store privacy回答、アプリ内privacy policy、web上のprivacy policyを同じ内容へ更新する。

### Privacy Policy追記案

共有機能を公開する際は、現行policyへ少なくとも次を追記する。法務確認前の製品要件であり、最終的な規約文ではない。

> 共有を利用しない場合、写真の検出結果、写真ライブラリの識別子、「これ好き」の記録は端末内に保存され、ねこのまどのサーバーへ送信されません。
>
> 招待制共有を有効にすると、送信者のウィジェット候補である最新20枚までの縮小画像、共有用の疑似匿名ID、世代と表示順序、肉球の反応と更新時刻をCloudflareのサービスへ送信します。写真の原本、写真ライブラリの識別子、ファイル名、EXIF、位置情報、氏名、メールアドレス、電話番号、連絡先、広告ID、push tokenは送信しません。
>
> 共有画像と肉球の反応内容は、確認済みの参加端末だけが復号できるよう暗号化します。サーバーには復号鍵を保存しません。ただしサーバーは、共有関係の存在、疑似匿名ID、暗号文の件数・容量・送信時刻、世代・順序、反応した参加者という運用metadataを処理します。招待リンクはLINE等の利用者が選んだ送信経路を通り、その経路は当社の端末間暗号化の対象外です。参加前に両端末の確認フレーズが一致することを確かめてください。
>
> サーバー上の共有画像は、一つの写真源につき最新20枚まで、かつ送信後30日以内に限定します。共有解除時は最初に取得権限を失効し、画像とlive database recordを削除します。削除に失敗した処理は完了まで再試行します。災害復旧用のD1 Time Travelには削除前のmetadataがWorkers Paidでは最大30日、Freeでは最大7日残り得るため、復旧を行った場合は削除記録を再適用します。画像暗号文を置くR2 objectは共有解除後に削除します。
>
> 機種変更、アプリの削除・再インストールでは共有鍵を引き継がず、相手からの再招待が必要です。共有解除後も、相手が端末へ保存した写真やスクリーンショットは当社または送信者から削除できません。共有dataを広告、tracking、販売、公開、AI学習へ利用しません。処理委託先はCloudflareです。共有dataの削除または問い合わせは、アプリ内の「共有を解除して削除」またはpolicy記載の連絡先から受け付けます。

D1の復旧保持期間は公開時の契約planと[公式limits](https://developers.cloudflare.com/d1/platform/limits/)を再確認する。復旧を実行する運用では、live dataだけを過去へ戻して削除済みparticipantを復活させないよう、別保全した削除台帳をrestore直後に再適用する。

## Cost envelope

2026-08-17時点の公式単価を使う。R2 Standardは10GB-month、Class A 100万回、Class B 1,000万回まで無料で、超過はそれぞれ`$0.015 / GB-month`、`$4.50 / 100万回`、`$0.36 / 100万回`、egressは無料である。[R2 pricing](https://developers.cloudflare.com/r2/pricing/)を正本とする。Workers Paidは月額`$5`に1,000万requestと3,000万CPU-msを含み、超過requestは`$0.30 / 100万回`である。[Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)を正本とする。D1 Paidは月250億row read、5,000万row write、5GBを含む。[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)を正本とする。価格は実装開始時と公開前に再確認する。

1 participantが一つの送信写真源を持つ前提では、保持量の絶対上限は約`10.16MiB × participant数`、R2 object数は`60 × participant数`である。10,000 participantsが全員上限まで保持すると約100GiBで、現在単価のR2 storageは無料枠超過分が概算`$1.4 / 月`である。これは暗号化overhead、日割り、Cloudflareの課金単位丸めを省いたorder estimateであり、請求額の保証ではない。

運用費を支配するのは保持量より世代の入れ替わり頻度である。`U=participants`、`G=1人あたり月間publish世代数`、`C=1世代で変わる20枚の割合`と置くと、差分転送時のR2 Class AとBはそれぞれ概ね`U × G × 60 × C`回になる。現在の選別は長期間表示していない写真を優先するため、新世代で大部分が入れ替わる可能性があり、通常は小差分になるとは仮定しない。

10,000 participants、全20枚入れ替え`C=1`、revision確認をWidget更新36回／日＋アプリ起動1回／日とする感度は次のとおりである。object転送はWorker requestへ数えない短時間の認可済み直接転送を仮定する。

| publish頻度 | R2 Class A / B | 現行単価による月額の概算 |
| --- | ---: | ---: |
| 月1回 | 各60万回 | Workers約`$5.33`＋R2 storage約`$1.4`、計`$7`前後 |
| 週1回（月4回） | 各240万回 | 上記＋R2 Class A約`$9`、計`$16`前後 |

表はD1超過、CPU超過、domain、税、監視を含まない。画像objectまで全てWorkerで中継するAPIなら、毎日全入れ替えの10,000 participantsでupload／download由来の最大3,600万request／月がさらに加わる。D1もgeneration、media、variant、delete、indexの実row write数次第でPaid込み5,000万write／月へ近づき得る。したがって、認可方式とobject転送経路を実装前に固定し、D1の`meta.rows_written`をload testで測る。

世代番号が変わっても同じ暗号文hashのobjectを再uploadせず、変化したfamily objectだけを差分転送することをcost上の必須条件とする。20分ごとのserver poll／uploadは実装しない。公開前には実測した`participants / active source / generations / changed objects / revision checks / R2 A・B / Worker requests・CPU / D1 rows`をこの式へ入れ直す。CloudflareのBudget Alertは通知であり支出を停止しないため、[Budget Alert](https://developers.cloudflare.com/billing/manage/budget-alerts/)に加えてWorkerのCPU／subrequest limitsと、アプリ・API側のparticipant／generation／upload quota・rate limitを設定する。

## 受け入れ条件

### ローカルアルバム

- 撮影日時順の猫写真grid、「すべて／好き」、既存ブラウザへの遷移が端末内dataだけで動く。
- アルバム閲覧によって個人用Like、Widget候補、1週間計測baselineが変わらない。
- 1週間計測中の端末にはinstallしない。

### 共有

- 共有集合が送信者の現在のWidget候補最大20枚と一致し、Like集合ではないことを自動testで検証する。
- 肉球のON/OFFでupload集合、世代、順序が変わらない。
- 同一の世代、順序、切り替え基準を両端末で復元できる。
- networkなしでも取得済み20枚の端末内rotationを継続できる。
- app起動またはWidget更新まで相手への反映が遅れても、壊れたplaceholderへ戻らない。
- 20枚それぞれのSmall / Medium / Largeが送信側アプリで生成済みのWidget派生と一致し、送信・受信Widget更新中にPhotoKit、Vision、crop、blur、resize、JPEG再圧縮を実行しない。
- APNs entitlement、通知permission、push token送信がない。
- R2とD1だけでは共有画像を復号できない。
- 招待link／QRに一回限りのenrollment secret以外の鍵がなく、room keyとcontent keyが含まれない。
- 招待先が端末内でkey pairを生成し、両端末のverification phraseが一致して招待者が明示承認するまでroom key envelopeを取得できない。
- linkを取得した第三者はpending enrollmentや利用妨害を試せても、確認なしにroom keyを取得できないことをintegration testで確認する。
- 招待linkのserver request／logへenrollment secretが含まれない一方、送信経路にはlink全体が見えること、phraseを誤確認すると攻撃者を承認し得ることをUIとpolicyが説明する。
- 機種変更・再インストール前の警告を承認しない限り共有を開始できない。
- 最新20枚、30日、unlink即時失効と物理削除再試行をserver integration testで確認する。
- 個人用Likeとpair reactionが別namespaceであり、相互に集計されない。

## 採用しないもの

- 肉球を共有commandにすること
- 「好き」だけを共有すること
- 原本upload
- APNs、silent push、通知
- email、password、電話番号を使うaccount
- 不特定多数への公開、検索、follow、公開URL
- 20分ごとのserver uploadまたはpollを写真rotationの前提にすること
- 相手の端末に保存されたcopyを遠隔で削除できるという表示
