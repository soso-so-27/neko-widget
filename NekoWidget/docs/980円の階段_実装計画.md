## 1. 体験期間（14日）の管理

### 1-1. 置き場所と形

新しい `TrialPeriodStore`（App targetだけ。Widget・Share Extension には入れない。ADR-025 決定3 と同じ境界 `docs/ADR-025:47`）。

```text
TrialPeriodRecord v1
  startedAt        体験の開始時刻
  maxObservedNow   起動・前面復帰のたびに更新する「これまでに見た最大の現在時刻」
  lastServerNowMs  サーバー応答から得た最新のサーバー時刻（任意）
  deviceState      unknown / consumedBitSet / consumedBitClear / unsupported
  endedAt          終了を確定した時刻（任意）
```

- 第1層：**Keychain**（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`、iCloud同期なし、App Groupなし）。既存の課金Keychainと同じ流儀（`NekoWidget/Services/BillingKeychainStore.swift:6-8`、ADR-025 決定1 `docs/ADR-025:21`）。iOSではアプリ削除後もKeychain項目が残る運用実績があり、再インストールで戻らない第1の壁になる。ただしAppleが文書で保証している挙動ではないので、第2層を置く。
- 注意：ADR-025 決定1 は「残存Keychainを新インストールの**権限の根拠にしない**」ために `BillingInstallationMarkerStore` を使う（`BillingKeychainStore.swift:698-723`）。体験記録は逆向き（残っていれば**制限する**方向）なので、残存を採用しても「払っていない人に権利を与える」失敗にはならない。
- Widget へは今の仕組みをそのまま使う：App が `.verified(validUntil: 体験終了時刻)` を `PersonalWidgetMembershipStore.publish` で書く（`Shared/PersonalWidgetMembershipStore.swift:64-88`、呼出は `NekoWidget/App/NekoWidgetApp.swift:152-164,176-183`）。Widget は体験という概念を知らなくてよい。App を一度も開かなくても、スナップショットの `validUntil` で Widget 側が止まる（`NekoWidgetTimelineProvider.swift:279-282`、`PersonalRediscoveryStore.swift:478-485` の「期限時刻に同じ写真の終端エントリ」）。

### 1-2. 再インストールで戻らないようにする方法の比較

| 方法 | できること | 難点 | 判定 |
|---|---|---|---|
| Keychain（上記） | 同じ端末での再インストールをほぼ防ぐ。ネットワーク不要 | Apple非保証。端末初期化・機種変更では消える | **採用（第1層）** |
| **DeviceCheck（2ビット）** | 端末＋開発者チームに紐づく2ビットをAppleが保存。アプリ削除・初期化後も残る。bit0＝「この端末で体験を使った」 | サーバーが要る（AppleのDeviceCheck APIへ、DeviceCheck用の.p8鍵で署名したJWTで問い合わせる）。保存できるのは2ビットと更新年月だけで、開始日は入らない。初回起動がオフラインなら確認できない | **採用（第2層）**。SharingService の Worker に小さな endpoint を1本足す（Cloudflare Workers は ES256 署名ができる）。鍵の有無は**未確認**（App Store Server API 鍵とは別物） |
| App Attest | アプリ本物性の証明。状態は保存できない | 体験管理の目的には過剰。保存は結局サーバーが要る | 見送り |
| サーバー記録（BillingAccountID 単位） | 正確な開始日を保持できる | BillingAccountID の発行は bootstrap が既定OFFで、発行に厳しい前提がある（`docs/ADR-025:19-20`）。初回起動で通信とID発行が必要になり「最初に何も聞かない」と衝突する | v1では見送り。将来 bootstrap を使うとき（購入時）に `startedAt` を一緒に記録する |

**推奨の組み合わせ**：Keychain＋DeviceCheck。判定の順は次のとおり。

```text
Keychainに記録あり → それを使う（DeviceCheckは背景で照合して deviceState を更新）
Keychainに記録なし、DeviceCheck bit0=1 → 体験は使用済み。体験後として開始（Keychainに endedAt 付きで記録）
Keychainに記録なし、DeviceCheck bit0=0 → 体験を開始。Keychainに記録し、bit0 を立てる
Keychainに記録なし、DeviceCheck 不通 → 体験を開始（ローカルのみ）。次回オンライン時に bit0 を照合・設定
```

受け入れるリスク：オフラインのまま再インストールを繰り返すと14日ずつ延びる。機種変更（Keychain `ThisDeviceOnly` は移らず、DeviceCheck は端末単位）では新しい端末で体験が始まる。これは「端末ごとに14日」と割り切る（Appleのお試しオファーは Apple ID 単位なので異なる。所有者が確認すること）。

### 1-3. 端末の日付を進められた・戻された場合

- 有効な「今」＝ `max(端末時刻, maxObservedNow)`。端末時刻を**戻しても**体験は延びない。
- 端末時刻を**進めた**場合は体験が早く終わる（利用者が損をする方向）。戻したあとも `maxObservedNow` が進んだままになるので、サーバー時刻が得られたときだけ `maxObservedNow` をサーバー時刻へ訂正する。サーバー時刻は、DeviceCheck endpoint の応答に `serverNowMs` を含める、または既存の権限応答の `evaluatedAtMs` を使う（`NekoWidget/Services/BillingClientCore.swift:505-519` に時刻ずれの検査がある）。
- 既存の時刻ずれの先例：Widget スナップショットは `recordedAt` が今より5分以上未来なら無効（`Shared/PersonalWidgetMembershipStore.swift:16`）。同じ5分を許容幅にする。
- 日数の数え方：`startedAt + 14×24時間` を終了時刻にする。「あと○日」は切り上げ表示。暦日やタイムゾーンでの計算は使わない。

### 1-4. 終了後の状態の持ち方

`TrialState`（App側の新しい型）：`notStarted / active(until:) / ended(at:) / unreadable`。

`MembershipAccessContext` に体験状態を合流させる（今の init は `PlusEntitlementState` だけから `personal` を作る：`MembershipAccessContext.swift:28-46`）。合流の順：

```text
Plus が grantsPlus → 今のまま（verified / indeterminate / inactive）
Plus が inactive または disabled で、体験 active → personal = .verified(validUntil: 体験終了)
Plus が inactive または disabled で、体験 ended → personal = .inactive
Plus が indeterminate（払っていた人のサーバー確認が取れない） → 今のまま（lastVerifiedUntil まで許可、以後は確認要求）
体験 unreadable（記録はあるが読めない） → 体験後と同じ扱い。「確認できません」画面は出さない
```

- `PlusPurchaseStore.entitlementState` の `didSet` が `membershipActions` を更新している（`PlusPurchaseStore.swift:203-208`）。体験を合流させるには、`PlusPurchaseStore` と `TrialPeriodStore` を束ねる1つの `MembershipAuthority`（新設）が `membershipActions`・環境値・Widget スナップショットの3つを更新する形にし、`NekoWidgetApp.swift:147-185` の `ProductionAppRootView` からその1つだけを参照する。
- 14日目の「あすから」の1行は、ホーム画面の既存の一回限り案内（`NekoWidget/Views/HomeView.swift:194-197,282` の `shouldOfferWidgetPlacementGuide`）と同じ形で、体験記録に `day14NoticeShownAt` を持たせて1回だけ出す。通知・全画面・カウントダウンは出さない。
- 「あと○日」は設定の中だけ（`SettingsView.swift:296-305` の会員プラン欄）。
- 有効フラグ：Info.plist の `MembershipAccessEnforced` を xcconfig 変数 `MEMBERSHIP_ACCESS_ENFORCED` にして、App と Widget の両 Info.plist が同じ変数を参照するようにする。両方が一致しないと Widget だけ止まる／止まらないが起きる（`Shared/PersonalWidgetMembershipStore.swift:45-47` は Widget の Bundle を読む）。

## 3. Plusの1画面を出す5か所と、出さない場面の守り方

### 3-1. 画面を1種類にする

今は2段階：`MembershipAccessNotice`（「会員プランで、うちの子との時間を楽しむ」＋「会員プランを見る」ボタン）→ `MembershipOfferSheet`（`MembershipAccessContext.swift:97-144`）。決定は「その場所に1画面だけ」「ボタンの文言は何が起きるか」なので、通知を経由せず直接シートを出す。

### 5-2. ファミリー共有（一度オンにすると戻せない）

今は3か所で `FAMILY_SHARED` を拒否している（第0章）。有効にするには次が要る。

1. **クライアント**：`isEligibleStoreKitTransaction` の `ownershipType == .purchased` を `.purchased || .familyShared` に（`PlusPurchaseStore.swift:777-788`）。`BillingFreshAccountAuthorization.swift:136` も同様。
2. **appAccountToken の問題**：クライアントは取引の `appAccountToken` から `BillingAccountID` を復元する（`PlusPurchaseStore.swift:571-579,633-636`）。家族側の端末に届く取引に、購入者が設定した token がそのまま入るかどうかは**未確認**（Apple の文書で確認が要る）。入らない場合、家族側は `.indeterminate` に落ちて「確認できません」になる。設計案：家族側の端末では自分の `BillingAccountID` を bootstrap し、`FAMILY_SHARED` の取引をその ID に「受益」として記録する。Server は `FAMILY_SHARED` のステータス1・4を、その受益 ID の権利として評価する。
3. **検証サービス**：`ownershipType !== PURCHASED` で拒否している行（`BillingVerificationService/src/apple-transaction.ts:81`）と、`billingAccountId` の UUID 必須（`:75`）を `FAMILY_SHARED` の場合に緩める。テスト：`test/apple-transaction.test.ts:82`、`test/apple-subscription-status.test.ts:221-235`、`test/apple-account-recovery.test.ts:68` は「拒否されること」を確認しているので書き換える。
4. **Worker**：`itemRestrictionRank` が `FAMILY_SHARED` を最も制限的な 9 にしている（`SharingService/src/billing-entitlement.ts:59-68`）。家族の受益を許可に変える。課金鍵の復旧は `PURCHASED` 限定のまま（`billing-recovery.ts:102,122`。家族側は復旧ではなく新規 bootstrap で足りる）。
5. **StoreKit 2 の挙動**：家族側にも `Transaction.currentEntitlements` と `Transaction.updates` で取引が届く。購入者がファミリーを抜ける・共有を切ると `revocationDate` 付きで届く（既存の失効処理 `PlusPurchaseStore.swift:563-606` がそのまま効く）。`Product.SubscriptionInfo.isFamilyShareable` で商品設定を読める。Sandbox でのファミリー共有の試験方法は**未確認**。
6. **文書**：ADR-025 決定4・5（`docs/ADR-025:85-89,98,125`）を ADR-027 で改訂。

**順番の提案**：App Store Connect で ON にするのは、1〜5 を実装して Sandbox で家族側の端末が Plus になることを確認したあとでよい。OFF→ON は後からできるが ON→OFF はできない（**未確認**：Apple の文書で「後からONにできる」ことを所有者が確認すること）。LP の「払うのは1人、使うのは家族」は ON にする時期に合わせて出す。

### 5-3. 既存の BillingAccountID／Server entitlement 設計との関係

- 購入者側は今の設計のまま（`appAccountToken = BillingAccountID`、Server の実効権限で `.serverConfirmed`、36時間の鮮度：`docs/ADR-025:37-41`、`PlusPurchaseStore.swift:671-723`）。
- 体験期間は Server を通らない。Server の実効権限は「払った人」だけを扱い、体験は App 内で完結する（1-4）。
- **販売の前提条件で未完了のもの**（今回の決定とは独立に残る）：bootstrap・取引記録・実効権限・復旧の各 runtime gate は App も Server も既定 OFF（`Config.xcconfig:38-48`、`docs/ADR-025:51-79`）。再インストール後の「購入を復元」は専用の復旧 protocol が有効になるまで古い口座を取り戻せない（`PlusPurchaseStore.swift:455-460`、`PLUS_BILLING_RECOVERY_ENABLED`）。これは審査要件 3.1.2「全端末で使えること」にも関わる（第6章）。
- まどの sponsorship（Server ADR-025）は 2-1 の決定でゲートに使わない。

## 6. Appleの審査上の注意

### 6-1. ガイドライン 3.1.1／3.1.2 との関係

- **3.1.1**：アプリ内のデジタル機能の開放は In-App Purchase で行う。Plus は StoreKit 2 の自動更新サブスクリプションなので適合（`docs/課金と商品化の導線.md:282`）。
- 3.1.1 の無料体験の記述は「お試しオファー」または「0円の非消耗型（名前は『14-day Trial』の形）」を例に挙げている。アプリ側が期間限定で有料機能を開放する形はこの文面に直接は載っていない。禁じられてはいないが、審査員が「体験はIAPで実装せよ」と言える根拠にはなる。設計文書も「指摘されたらお試しオファーに切り替える」としている。
- **3.1.2(a)**：価格・期間・自動更新・含まれる内容を明確に、解約方法と利用規約・プライバシーへの到達、そして**利用者の全端末で契約が使えること**。今の Plus 画面は規約（Apple標準EULA）とプライバシーのリンクを持つ（`MembershipOfferView.swift:266-275`）。「全端末」は、再インストール・機種変更後の復元が成立していることが必要（5-3）。ファミリー共有を ON にしたら、家族側の端末で Plus になることも同じ要件に入る。
- **3.1.2(b)/(c)**：契約の変更・ダウングレードは1商品なので該当なし。
- 審査提出時：App Review 用のメモに「初回起動から14日間はアプリ側で全機能を開放している。15日目から Plus」と書き、審査員が Plus 画面に設定から到達できることを示す。Sandbox テスターの手順は既存の本人限定テスト（`MembershipOfferModel.swift:545-687`、`SettingsView.swift:307-313`）を流用。

## 7. 既存の TestFlight 利用者（1台3まど）への移行で守ること

### 決定（2026-10-20、所有者「調査の上、最適と思われる方針でそれぞれ進めて」→ 決めて ADR-027 に記録）

| # | 項目 | 決定 | 理由 |
|---|---|---|---|
| 1 | まどの**合計**上限 | **10**（自分＋参加。無料でもPlusでも同じ） | 招待で入るのは無料で、プランで変えない原則。デコード上限20の半分で、整理の案内は今の仕組みを使う |
| 2 | アルバムの無料範囲 | **一覧は無料。月のまとめ・季節のムービーを開くのがPlus** | 「見る」は残し、「育つもの」だけを有料に。設計表の「自動アルバムの更新」＝新しい月のまとめ・ムービーを開けること |
| 3 | 体験後の Widget の pause アイコン | **消して写真だけにする** | 設計の「ロックのマークを出さない」。写真をタップすればアプリにPlusのカードがある |
| 4 | Family Sharing を ON にする時期 | **PR 8 の実装後、Sandbox で家族側の端末がPlusになることを確認してから** | ON→OFF は戻せない |
| 5 | 体験を「端末ごとに14日」と割り切るか | **割り切る** | 機種変更で再び14日になるのは受け入れる。Apple ID単位にするにはサーバー記録が要り、「最初に何も聞かない」と衝突する |
| 6 | DeviceCheck | **使わない**。Keychain だけで始める | サーバーの endpoint と Apple 側の鍵が要り、980円の体験を守るには過剰。悪用が見えたら足す。**PR 7 は行わない** |
| 7 | 商品ID | **`jp.nekowidget.plus.monthly`** | 既存の Sandbox 用スクリプトと同じ。App Store Connect に同じIDの商品があればそれを使う |

### 追加決定（2026-10-20昼、所有者）：まどは作った人がPlusで続ける

- `createFirstOwnWindow` は**体験中は allowed、体験後は membershipRequired**（「1つ目はずっと無料」を撤回）。
- 自分が作ったまどへの送信（作った人）の判定を足し、体験後・Plusなしは membershipRequired。止まっているまどへはサーバーも拒否する（種別は Codex が決める）。招待されたまどでの送信（`addSharedContent`）は常に allowed のまま。
- 体験期間（PR 3）の対象に「まどを作る・作ったまどを続ける」を含める。
- Plus の画面の入口に「このまどを続ける」（作った人が止まったまどを開いたとき）を追加（PR 5・6）。
- 2-1 の「`addSharedContent` を常時許可」は招待された側についてはそのまま。sponsorship のコードは、作った人のPlusで続く形に合うので、停止ではなく作り直しの候補になる。
- 担当：サーバー側（止まっているまどの判定と拒否）は Codex。まどの画面（止まっている案内・続けるボタン・メンバーへの説明、`PairingView.swift`・`FamilyWindowView.swift`）はメインセッション。Policy とその呼び出しは PR 2 の続き。

決定6により、1-2 の判定順は「Keychain に記録あり → それを使う／なし → 体験を開始」の2行になり、`deviceState`・`lastServerNowMs` は v1 では持たない（サーバー時刻の訂正は、既存の権限応答の `evaluatedAtMs` が得られたときだけ行う）。
