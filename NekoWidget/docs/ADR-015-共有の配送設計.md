# ADR-015：共有は期限付き・容量上限付きの暗号化配送箱にする

日付: 2026-08-20
状態: 採用・未実装
置換対象: [ADR-009](ADR-009-ローカルアルバムと招待制共有.md)

> **本ADRは設計判断だけであり、まだ実装していない。**
> Server、APNs、E2E配送、Share Extension、招待、課金、UGC対応をこのADRの採用だけで有効化しない。既存のADR-009向け実装を本ADRの代用として公開しない。
> Build 21では、製品レビューのため本ADRの静的画面だけを表示する。運用フラグ、API URL、写真同期はOFFのままで、招待、鍵、識別子、写真の送信は行わない。

## 背景

製品には、既にある写真を発掘する「過去の流れ」と、いま撮った写真を家族へ届ける「現在の流れ」の両方が必要になった。

- 過去の流れ: 既にある写真 → 窓に出る → 肉球 → 溜まる → 本
- 現在の流れ: いま撮る → 家族の窓へ届く → 送り返される → 課金

ADR-009は、過去写真の最大20枚を一日一度すべて再発行し、APNsを使わず、app起動またはWidget更新時に同期する設計だった。これは静かな日次共有には適していたが、1枚を明示的にすぐ届ける現在の流れには適さない。

特に、最大20枚を毎日再発行する上限モデルでは、10,000のactive publishing sourceについて月600万canonical PUTと月30万manifest PUT、合計月630万R2 Class A操作が発生する。ADR-009の直接従量課金見積は月`$80〜245`であり、現在のD1 tableとindexの書き込み増幅まで含めた保守的な再計算では、A相当の小さい画像でも月`$118`が下限になる。

本ADRのD案は、10,000人が一人一日一枚を送り、暗号文が平均約600KB、無料利用者はACK後7日から未受領30日まで、10%の有料利用者だけが最長365日保持する感度で、Cloudflareの直接費を月`$9〜11`と見積もる。これはWorkers、R2、D1の現在単価による設計比較値であり、税、為替、domain、observability、abuse、moderation、support、AppleのIAP手数料を含まない。実装後は実際の平均bytes、ACKまでの時間、retry、read/write行数、取得回数と突き合わせて更新する。

即時写真をこの日次generationへ差し込むと、1枚送るたびに集合全体の置換、再取得、整合性管理が必要になる。したがって、共有の保存単位を世代全体から1枚の不変なmessageへ変更する。

## ADR-009から置き換える判断

| ADR-009 | 本ADR |
|---|---|
| 最大20枚を毎日丸ごと再発行 | 1枚ずつ追記する。過去写真も1日1枚 |
| APNsを使わない | APNsを使う。ただしWidget更新を保証しない |
| 復旧accountを作らず、鍵喪失後は再招待 | Serverへ鍵を預けない方針は維持する。残存端末からの復旧だけを許し、全端末喪失時の復旧不可を購入前に明示する |

ADR-009のローカルアルバムに関する判断は履歴として残す。招待制共有の配送、保持、費用、APNs、鍵、privacy、課金に関する正本は本ADRとする。

## 決定1：共有は追記型の二つの流れにする

家族の窓には、二種類の写真が届く。

- `memory`: 過去から一日一枚だけ届ける写真
- `live`: 利用者がShare Extensionから明示的に送る写真

どちらも一送信を一つの不変オブジェクトとして追記する。一度commitした暗号文、hash、sender、種別、作成時刻を別内容で置き換えない。

過去写真は最大20枚を毎日再発行しない。各送信者について、窓の初期化時に「毎日1枚、自動で送りますか」を明示的に選ばせ、**既定はOFF**とする。OFFでは過去写真を自動送信しない。ONを選んだ窓だけ、一日一枚を自動送信し、受信端末が検証済み写真をローカルへ蓄積してWidgetで巡回する。この設定は窓ごと、送信者ごとに保存し、後から設定で停止できる。

窓を初めて作るときだけ、アプリが選んだ最大20枚を利用者へ見せ、「これを送りますか」の一括確認後に初期化できる。この初期化も20個の独立した不変オブジェクトとして扱い、一つの世代objectへまとめない。

初期化の最大20枚は、一つの窓につき一回だけ、通常の一日5枚の無料送信枠とは別に許可する。Serverはspace lineageへ`initialBootstrapGrantConsumedAt`と初期化requestのidempotency情報を保存し、同じ窓のreset、再招待、初期化のやり直しでgrantを再付与しない。途中失敗は同じgrantと同じobject集合を再開し、成功済みobjectを二重送信または日次枠へ二重計上しない。窓の削除後も、同じ窓を作り直してgrantを再取得できないよう、消費済み事実を復旧不能な写真metadataとは分離した最小のtombstoneとして保持する。

送ったものだけを家族の窓へ入れる。猫写真であっても背景の人や部屋を自動送信しない。

## 決定2：画像仕様を全planで共通にする

一写真につきcanonical previewを一つだけ生成する。

- aspect ratioを維持し、長辺を最大2,048pxとする。元画像が小さい場合は拡大しない
- EXIF、GPS、ファイル名、PhotoKit local identifier、その他のsource metadataを削除する
- sRGBへ正規化する
- 平均500〜700KBを目安とする
- 暗号文を1MiB以下とするhard capを設ける
- hard cap内で受け入れ品質を維持できなければ送信しない
- Small、Medium、Largeを別objectとして送らず、受信端末が同じcanonicalから生成する

原本の撮影日時は画像metadataとして残さず、**認証付き暗号化manifestの中へ撮影日時を入れる**。D1、R2 object metadata、URL、application logへ平文で出さない。受信端末は復号後の撮影日時を、過去写真の巡回順、誕生日基準の年齢アルバム、肉球写真のPDF撮影日順に使用する。撮影日時が取得できない写真は、その欠損を暗号化manifest内で明示し、Serverや受信端末がupload時刻を撮影日時として捏造しない。

無料と有料で画質を変えない。写真の見栄えは製品体験そのものなので、低画質を無料planの制約にしない。

## 決定3：1送信を二段階でcommitする

配送は次の順で行う。

1. `reserve`: member署名、server time、送信数、暗号文bytes、object数、idempotency keyを検証して短命な予約を作る
2. `PUT`: 暗号文一つをprivate R2 objectへuploadする
3. `commit`: objectのsizeとhashを検証し、D1のmomentをimmutableな公開状態にする
4. `APNs`: commit済みmomentがあることだけを受信端末へ通知する
5. `receive`: commit時に固定した受信memberごとに取得、認証、復号し、端末内の検証済みローカル領域へ保存する
6. `ACK`: ローカル保存が完了した受信member自身のdeliveryへACKを返す

3人以上の窓でもACKをmoment全体の単一状態にしない。commit時の受信member集合を固定して、`moment_delivery`を受信memberごとに作る。後から窓へ加わったmemberへ過去のmomentを自動公開せず、必要なら新しい送信として明示的に届ける。

R2とD1を一つの原子的transactionとはみなさない。PUT後にcommitされなかったobjectと、予約だけで終わったrowは短いTTLとcleanup jobで削除する。retryは同じidempotency key、payload hash、暗号文を使い、送信枠を二重消費しない。

Share Extensionは、選ばれた画像をApp Groupのoutboxへ安全にcopyし、metadata除去、downsample、暗号化を終えた暗号文だけをbackground `URLSession`で送信する。Extensionの終了を成功扱いにせず、containing appが同じoutboxとbackground sessionを引き継げる構造にする。

## 決定4：D1には配送metadataだけを置く

D1のmomentには、少なくとも次だけを保存する。

- opaque moment ID
- 窓を表すspace ID
- space内だけで有効なsender member ID
- `memory`または`live`
- server作成時刻
- 暗号文sizeとhash
- `expiresAt`
- 鍵世代
- reserved、committed、expired等のobject全体の配送状態
- space lineageごとの初期化grant消費時刻と、その初期化requestの最小idempotency情報

受信memberごとの`moment_delivery`には、space内だけで有効な受信member ID、pending、acknowledged、expired、revoked等の状態、ACK時刻、個別の取得期限だけを保存する。最初の一人のACKを他の受信者のACKとして扱わない。

D1へ次を保存しない。

- 写真本文または復号可能なpreview
- EXIF
- GPSまたは位置情報
- ファイル名
- PhotoKit local identifier
- 原本の撮影日時
- room key、世代鍵、写真鍵の平文

R2 objectは公開URLにせず、space credentialとmember署名を検証した短時間の取得経路だけを提供する。Application logへ写真、invite secret、object URL、room key、暗号文hashを記録しない。

## 決定5：Serverは期限付き配送箱であり、保管庫ではない

無料版では、各受信memberの取得権を次の早い方で個別に失効させる。

- その受信memberのACK後7日
- commit後、未受領のまま30日
- そのmemberのunlinkまたはblock、space削除による即時の権限失効

R2暗号文は、commit時に固定した全受信memberのdeliveryがexpiredまたはrevokedになってから物理削除を再試行する。最初の受信者のACKだけでobjectを削除せず、まだpendingの受信者の30日枠を短縮しない。全受信者の個別期限のうち最後の期限がobjectの削除下限になる。

受信済み写真は端末のローカル履歴へ残せるが、これは写真アプリ、iCloud、またはserver backupではない。利用者が写真アプリへ明示保存したcopyやscreenshotは、送信者が回収できない。

有料履歴を導入する場合もpreviewだけを最長365日保持し、期間、枚数、総bytesのabsolute capをすべて設ける。無期限保持と原本保持は提供しない。有料履歴は需要、鍵引き継ぎ、downgrade、削除、StoreKit復元を実機で検証した後の別releaseとし、無料配送と同時には実装しない。

## 決定6：鍵は世代管理し、Serverへ預けない

各写真を固有のmedia keyで認証付き暗号化し、そのmedia keyを窓の現在の世代鍵でwrapする。Serverは暗号文とwrapped keyを運べるが、写真、media key、世代鍵を復号できない。

- memberを追加するときは、承認済みの既存端末が現在の世代鍵を新memberのpublic key向けにwrapする
- memberを除外またはblockしたときは取得権限を直ちに失効し、以後の送信に使う世代鍵を更新する
- 除外前に相手が保存、復号、撮影したcopyは回収できない
- 一台だけを失った場合、残っている承認済み端末から再招待し、保持に必要な鍵を新端末向けにwrapできる
- すべての参加端末が鍵を失った場合、Serverだけからは復旧できない
- v1では復旧account、server escrow、運営者用master keyを作らない

有料履歴を購入しても、StoreKitが復元するのは購入権であり暗号鍵ではない。保持期間を延長する操作はD1の`expiresAt`を変更するだけで、再暗号化を必要としないが、保持中の写真を読むための鍵世代は参加端末が維持する必要がある。

## 決定7：課金は量と期間と窓の数に置く

初回releaseは無料版だけを実装し、送信頻度、返信率、窓の閲覧率を確認する。有料版は観測後に別判断で追加する。

| | 無料 | 将来の有料 |
|---|---|---|
| 送信数 | 1日5枚 | 1日20枚 |
| Server履歴 | ACK後7日／未受領30日 | 最長365日。枚数・bytes上限も併用 |
| 家族の窓 | 1つ | 複数 |
| 画質 | 長辺2,048px、同一品質 | 無料と同一品質 |

課金の対象は送信数、共有履歴の長さ、家族の窓の数である。画質、APNs、WidgetKit pushそのものを課金対象にしない。

送信枠、共有履歴、窓の数はapp内のデジタル機能なので、App Storeで提供する場合はIn-App Purchaseを使う。購入、復元、変更、解約のUIはcontaining appに置き、Share Extension内で購入させない。

有料履歴は「共有履歴365日」と呼び、「バックアップ容量」と呼ばない。購入前に次をそのまま表示する。

> 共有履歴はバックアップではありません。保持期間を過ぎた写真は削除されます。
> すべての参加端末が鍵を失うと、保持期間内でも復元できません。

## 決定8：非公開の家族間でもUGC安全機構を同時に出す

招待した家族だけの窓にもApp Review Guideline 1.2を適用する。共有機能を有効にするreleaseには、次を同時に含める。

- 受信写真を通報する導線
- 相手をblockし、取得権限とローカル表示を直ちに止める導線
- 利用者が運営者へ到達できる公開連絡先
- 通報を適時確認し、必要な失効と削除を行う運用手順

E2Eの通常配送では運営者が写真を読めない。通報時だけ、利用者の明示同意を得て当該preview一枚をmoderation用公開鍵へ別途暗号化し、通常共有とは分離した短い保持期限で扱う。この例外を通報前とprivacy policyで説明する。

UGC対応、公開連絡先、対応担当、community standard、App Review用の二端末demoまたは完全なdemo modeを用意できるまで共有をreleaseしない。

### 投稿前filterの実装手段は未決定

本ADRでは、`SensitiveContentAnalysis`を使うか、別の端末内modelを使うか、または通報とblockを中心とする別の適合方法を採るかを決定しない。`SensitiveContentAnalysis`が扱う範囲とGuideline 1.2が求める範囲を同一と仮定しない。

共有の実装へ着手する前に、App Review Guideline 1.2の最新要件、対象category、誤判定時の扱い、E2Eとの境界、実機検証方法を別のmoderation判断として確定する。その判断が承認されるまで、写真upload処理を実装しない。したがって、手段未決定の「端末内filter」を本ADRの実装済みrelease gateとはしない。

## 決定9：APNsを使うが、Widget更新を即時保証しない

Serverはcommit済みmomentを知らせるためにAPNsを使う。通知payloadへ写真、caption、member名、鍵、object URLを入れず、認証後に取得すべき変更があることだけを伝える。

- iOS 26以上ではWidgetKit pushをbest effortの更新契機として使う
- それ以前では通常のuser notificationを使い、窓はapp起動またはWidget timeline更新時に追従する
- すべてのOSで、送信から数秒以内のWidget表示を契約にしない
- timeline更新、app起動時の同期、最後に検証済みのローカルcacheをfallbackとして維持する

WidgetKit pushはsystemが予算管理し、opportunisticに配送する。製品訴求は「すぐ届く」ではなく、**「届いたら知らせる」**とする。

## 決定10：Privacy申告を共有releaseと同時に変更する

E2E暗号化であっても、写真の暗号文と識別子を端末外へ送り保持する以上、「データを収集しません」を維持しない。共有を有効にするreleaseでは、実装済みの範囲に応じて少なくとも次を`App Functionality`、`User linked`、`Trackingなし`として申告する。

- Photos or Videos: 暗号化canonical preview
- User ID: space固有のmember ID
- Device ID: APNsまたはWidgetKit push token
- Product Interaction: 送信、受領、reaction、利用枠
- Purchase History: StoreKit entitlementをServerで検証する場合

`PrivacyInfo.xcprivacy`、App Store ConnectのApp Privacy回答、app内privacy policy、公開web policy、写真access前の説明、App Review Notesを同じreleaseで更新する。Cloudflareが暗号文と配送metadataを処理すること、運営者が通常写真を復号できないこと、Serverが知り得る件数、size、時刻、窓内ID、plan、保持と削除、通報時だけ生じるE2E例外を説明する。

共有を実装していないbuildでは申告を先行変更しない。

## 決定11：窓では現在と過去を別の表示枠として扱う

`live`を既存の過去写真rotationへ無作為に混ぜない。窓は次の固定規則で表示する。

1. 新しく届いた`live`を2〜4時間、または反応があるまで優先表示する
2. 「いま届いた」と送り主を表示する
3. 複数届いた場合は最新一枚と残り件数を表示する
4. 優先期間を過ぎた`live`は共有履歴へ移す
5. 優先する`live`がないときだけ、蓄積済みの過去写真を巡回する
6. 「届いた写真を優先」の設定を用意する

一つのWidgetは一つの窓だけを表示する。複数の窓の写真を一つのWidgetで混ぜない。

## 対象外

本ADRのv1対象は、家族の窓に招待された少人数が双方向に送る場合だけである。

団体向けの一方向配信は別システムとする。団体が一つの公開objectを複数の購読者へ配信する設計であり、家族向けE2E objectを購読者数だけ複製しない。購読者同士を見せず、団体にも個々の購読者を見せないprivacy、保持、課金、moderationを別ADRで決める。**団体向け配信はv2であり、ADR-015の実装範囲外である。**

原本保持、無期限保持、server鍵escrow、復旧account、団体向け配信、共有の有料版はv1に含めない。

## 実装前のrelease gate

本ADRのレビューと承認が終わるまで、共有のServer、APNs、E2E配送、Share Extension、招待、課金を実装しない。

実装を開始する場合も、少なくとも次をrelease条件とする。

- 一送信が一不変objectになり、旧20枚generationを再発行しない
- retryが送信枠またはobjectを二重作成しない
- hard byte capをClientとServerの双方で拒否できる
- ACK後7日、未受領30日、unlink、blockの削除が収束する
- 3人以上の窓で、ある受信者のACKが別の未受領者の30日枠を短縮しない
- member除外後の新しい写真を旧世代鍵で復号できない
- 一台喪失からのpeer-assisted復旧と、全端末喪失時の復旧不可表示を実機で確認する
- Share Extensionのbackground uploadを、終了、再起動、offline、retryで検証する
- iOS 26のWidgetKit pushと、それ以前の通常通知fallbackをsigned実機で確認する
- 別のmoderation判断で確定したGuideline 1.2対応と、通報、block、公開連絡先、対応手順を共有と同時に提供する
- Privacy申告、policy、Review Notes、IAP説明が実装と一致する
- App Group、Keychain、APNs entitlementをApp、Widget、Share Extensionの署名済みarchiveで検証する
