# 実機技術検証チェックリスト

## 目的

TestFlightでiPhoneへ配布したビルドについて、実ライブラリ上の安定性、PhotoKit、段階スキャン、アルバム、WidgetKit、App Group、診断ログおよび猫写真の選別精度を同じ形式で記録する。

この文書では、次の2つを混同しない。

- **純粋な猫検出**：画像内に実在する猫が認識できる形で写っているか。
- **製品としての正解**：自分の実猫が主役で、「うちの子」の表示候補へ採用したい写真か。

他人の実猫や背景へ小さく写った猫は純粋な猫検出では正解になり得るが、製品としては不正解である。ぬいぐるみ、絵、テレビや画面内の猫、犬などは両方で不正解とする。

## 既知の前提

- 最低対応OSはiOS 17.1である。
- バックグラウンド同期はbest effortであり、正しさは起動時・フォアグラウンド復帰時の同期で担保する。
- WidgetKitのtimeline entryは指定時刻ちょうどの表示を保証しない。
- 写真シャッフルは設定時のアルバム内容をスナップショットとして扱い、アルバムへの後日追加を自動反映しない。この挙動は既知であり、本アプリの不具合には数えない。
- Simulatorの1,000枚テストはピーク76.1 MiBで完走済みだが、実機のjetsam安全性を保証するものではない。
- 全件スキャン速度は実機で測定する。速報表示が成立する限り、速度だけを理由に先行最適化しない。

## 11. 診断ログと検証JSON

### 診断ログで確認できること

- AppとWidgetの起動、権限status、スキャン開始・進捗・完了
- quick/full phaseごとのdetected、noCat、screenshots、burst duplicates、Deferred、Failed、reusedの集計
- 開始と完了timestampから求める概算所要時間
- thumbnail、Widget cache、manifest、timeline、画像読込の成否
- like操作、アルバム同期、App Group越しのWidgetログ

quickとfullの`Vision phase summary`は、それぞれの処理範囲の集計である。全体内訳が必要な場合は両phaseを合算し、最終的な正本は確定後の検証JSONとする。

### 検証JSONで確認できること

- `scanState`のphase、result kind、総数、処理数、猫数、Deferred、最古日
- active settingsと`analysisFingerprint`
- assetごとの機械判定status
- detected assetのconfidence、bounding box、area ratio、cat count
- screenshot、burst、favorite、like、表示履歴

精度集計では、確定後のJSONを使い、次の条件でactiveなレコードだけへ絞る。

```text
snapshot.scanState.phase == "completed"
snapshot.scanState.resultKind == "final"
asset.analysisFingerprint == snapshot.settings.analysisFingerprint
```

### 現行ログとJSONだけでは確認できないこと

- 写真内容に対する人間の正解
- TP、FP、FN、TN
- 他人の猫、ぬいぐるみ、絵、テレビ、スクリーンショット、小さな写り込み、犬などの誤検出理由
- noCatになったassetの閾値適用前confidenceやbounding box
- 実際のクロップの見切れ
- jetsam、クラッシュスタック、ピークメモリ実数

`noCat`の`cat`は現在`.none`として保存されるため、検証JSONから「信頼度が少し不足した」「面積だけ不足した」などを復元することはできない。

## 12. 検出精度の定義

### 12.1 評価対象

active fingerprintのうち、次の2 statusを混同行列の対象とする。

- **機械陽性 P**：`analysisStatus == detected && cat.detected == true`
- **機械陰性 N**：`analysisStatus == noCat`

次は混同行列へ直接入れず、別集計する。

- `unavailableLocally`：coverage gap
- `failed`：coverage gap
- `excludedScreenshot`：意図したpolicy exclusion
- `excludedBurstDuplicate`：意図したpolicy exclusion

### 12.2 人手ラベル

各写真へ次の2軸を付ける。

#### 猫存在ラベル

- `realCat`：実在する猫が認識できる形で写っている
- `noRealCat`：実在する猫が写っていない
- `uncertain`：判定不能

他人の実猫と背景へ小さく写った実猫は`realCat`である。ぬいぐるみ、絵、テレビや端末画面内だけの猫は`noRealCat`とする。

#### 製品ラベル

- `keep`：自分の実猫が主役で、表示候補へ採用したい
- `reject`：製品候補へ採用しない
- `uncertain`：判定保留

`keep`は、アルゴリズムのconfidenceや8%面積閾値を見ず、人間が写真そのものを見て決める。アルゴリズムの条件を人手正解へ流用すると、評価が循環するためである。

### 12.3 純粋な猫検出の混同行列

- **Cat TP**：Pかつ`realCat`
- **Cat FP**：Pかつ`noRealCat`
- **Cat FN**：Nかつ`realCat`
- **Cat TN**：Nかつ`noRealCat`

```text
Cat Precision = Cat TP / (Cat TP + Cat FP)
Cat Recall    = Cat TP / (Cat TP + Cat FN)
Cat F1        = 2 * Precision * Recall / (Precision + Recall)
```

### 12.4 製品としての混同行列

- **Product TP**：Pかつ`keep`
- **Product FP**：Pかつ`reject`
- **Product FN**：Nかつ`keep`
- **Product TN**：Nかつ`reject`

```text
Product Precision = Product TP / (Product TP + Product FP)
Product Recall    = Product TP / (Product TP + Product FN)
Product F1        = 2 * Precision * Recall / (Precision + Recall)
```

V1の主要指標はProduct PrecisionとProduct Recallである。Cat PrecisionとCat Recallは、Vision相当の猫存在判定と製品選別の問題を切り分ける診断値として併記する。

## 13. Coverageとpolicy exclusion

次を混同行列と並べて必ず報告する。

| status | 件数 | 扱い |
| --- | ---: | --- |
| detected | | 混同行列 P |
| noCat | | 混同行列 N |
| unavailableLocally | | coverage gap |
| failed | | coverage gap |
| excludedScreenshot | | policy exclusion |
| excludedBurstDuplicate | | policy exclusion |

分析可能な対象に対するcoverageは、次で記録する。

```text
Analysis Coverage = (detected + noCat)
                  / (detected + noCat + unavailableLocally + failed)
```

スクリーンショットと連写重複は設計上先に除外するため、このcoverageの分母には入れない。`unavailableLocally`と`failed`を自動的にFNへ数えると、猫検出性能と取得・処理失敗を混同するため避ける。

製品全体としての取りこぼしを評価したい場合は、coverage gapに含まれる写真も人手確認したうえで、別名のend-to-end指標として報告する。

## 14. 誤検出taxonomy

Product FPには、主な理由を1つ必須で付ける。複数該当する場合は、表の上にある理由を優先し、補足をnotesへ書く。

| reason | 定義 |
| --- | --- |
| `screenshot` | PhotoKit上のスクリーンショット除外をすり抜けた保存画像 |
| `tvOrScreen` | テレビ、スマートフォン、PC、印刷物などの画面・媒体内だけに猫がいる |
| `illustration` | 絵、漫画、アニメ、ロゴ、置物など |
| `plush` | 猫のぬいぐるみ |
| `otherPersonCat` | 実猫だが自分の猫ではない |
| `smallIncidentalCat` | 自分の猫だが背景の小さな写り込みで、主役ではない |
| `dogOrOtherAnimal` | 犬など別の動物を猫として採用した |
| `noCat` | 猫や猫に似た対象が見当たらない |
| `other` | 上記以外。notes必須 |
| `uncertain` | 人手でも判断できない。指標の分母から除外して件数を併記 |

連写は写真単体のFP理由と分け、burst単位で次を数える。

- **`badBurstRepresentative`**：1枚へ絞る動作自体は正しいが、残した代表より除外側に明らかに良い写真がある。

`badBurstRepresentative`は猫検出のFP/FNへ混ぜず、連写代表選択の品質欠陥として独立報告する。

## 15. コード追加なしの暫定測定

### 15.1 実ライブラリでProduct Precisionを測る

2. 全件スキャンを確定まで完走する。

5. アルバム全件を目視し、猫存在ラベル、製品ラベル、Product FP理由を外部表へ記録する。
6. 検証JSONのdetected数とアルバム件数が一致することを確認する。

アルバム上限、date range、候補の並べ替えにより全detectedが入っていない場合、この方法で得られるのは「アルバム採用subsetの精度」であり、全機械陽性のPrecisionとは表記しない。

### 15.2 既知の小さな集合でRecallを測る

1. 自分の猫が主役、他人の猫、猫なし、ぬいぐるみ、絵、テレビ、スクリーンショット、小さな写り込み、犬、連写を含む検証集合を作る。
2. アプリを見ずに全写真へ人手ラベルを先に付け、正解件数を固定する。
3. Limited Accessでその集合だけを許可する。
4. 全件確定後のアルバム、診断ログ、検証JSONを保存する。
5. 元の正解表と照合し、Cat TP/FP/FN/TNとProduct TP/FP/FN/TNを数える。
6. screenshot、burst duplicate、Deferred、Failedを別欄へ記録する。

この方法は検証集合内では正確だが、実ライブラリ全体のRecallを保証しない。

### 15.3 陰性を標本調査する場合

実ライブラリ全体のnoCatを目視できない場合は、無作為標本であること、母数、標本数、選び方を記録する。

noCat総数を`N_total`、無作為標本数を`n`、標本中のProduct FNを`k`とした簡易推定は次になる。

```text
Estimated Product FN = N_total * k / n
Estimated Product Recall = Product TP
                         / (Product TP + Estimated Product FN)
```

これは推定値であり、実数のTP/FP/FN表とは分ける。現在のアプリにはseed固定の無作為review導線がないため、「新しい順の100枚」など便宜的な抽出は偏りがあり、正式なRecallには使わない。

## 17. 正式な実ライブラリ精度測定に必要な最小追加

現行UIは全detectedとnoCatを写真付きで対応付けて確認できないため、実ライブラリ全体のTP/FP/FNを厳密に測るには、将来次の最小機能を追加する。

1. snapshotのdetected/noCatを既存の写真loaderで1枚ずつ表示する「検出検証」画面
2. `keep / reject / uncertain`、猫存在ラベル、誤検出reasonを保存する操作
3. analysis fingerprint付きの別検証JSONへ保存し、productionのLibrarySnapshot schemaとは分離
4. 全件またはseed固定の無作為標本を選ぶreview queue
5. TP/FP/FN/TN、coverage、reason別件数、母数、標本数、seedをJSONまたはCSVでexport
6. 共有用exportではlocalIdentifierをhash化し、写真本体を含めない

閾値調整まで行う場合だけ、閾値適用前の最大cat confidence、bounding box、area ratioを別のdetector traceとして保存する。TP/FP/FNを数えるだけなら必須ではない。
