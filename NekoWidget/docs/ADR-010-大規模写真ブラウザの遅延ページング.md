# ADR-010：大規模写真ブラウザは標準の遅延ページングを使う

- 状態：実装済み・実機計測待ち
- 日付：2026-08-17
- 対象：検出済み約898枚を左右に送る写真ブラウザ

## 背景

Build 10では、選択のたびにページ集合を現在前後へ入れ替えていた実装をやめ、全写真を固定順の`TabView(.page)`へ渡した。これによりOS標準の指追従、慣性、snap、端の跳ね返りを取り戻した。

一方、SwiftUIの`TabView(.page)`には、898件のpage bodyとstateを必要時だけ生成するという公開契約がない。PhotoKitの明示preheatは現在±2枚、最大5枚に制限していても、container側の初期化範囲をコードから証明できない。Build 10はすでにTestFlightへ送ったため、まず実機で操作上の問題を確認し、後続開発branchで構造的な上限を設ける。1週間計測は2026-08-17に撤回済みであり、端末へ別buildを追加しない制約はない。

Appleは[`LazyHStack`](https://developer.apple.com/documentation/swiftui/lazyhstack)を画面表示に必要なitemだけ作るcontainerとして説明し、[`scrollTargetBehavior(.paging)`](https://developer.apple.com/documentation/swiftui/scrolltargetbehavior/paging)をcontainer境界へsettleする標準pagingとして提供している。

## 判断

後続branchの写真ブラウザは次の構造を正本とする。

- 水平`ScrollView`
- `LazyHStack(spacing: 0)`
- 各pageを`containerRelativeFrame`で表示領域と同寸法にする
- `scrollTargetLayout()`と`scrollTargetBehavior(.paging)`を使う
- `scrollPosition(id:)`へ現在の写真identifierをbindし、Widget deep linkの初期位置を維持する
- 有限配列の先頭／末尾でOS標準のbounceを使い、loopを作らない
- PhotoKit preheatは現在±2枚、最大5 identifierのままにする
- 画面外へ出たrequestをcancelし、decode済み`UIImage`を解放する

独自`DragGesture`、offset計算、速度判定、snap animationは実装しない。

## 計測instrumentation

写真browserを開いて500ms後に、1回だけ次を`SharedLog`へ記録する。写真identifierや画像内容は記録しない。

- `page_count`
- `requested_page_position`
- `settled_page_position`
- `page_model_prepare_ms`
- `construction_to_appear_ms`
- `constructed_pages_500ms`
- `explicit_preheat_pages`

`constructed_pages_500ms`は、`LazyHStack`がitem builderを呼び、page wrapperを実際に構築したunique件数である。全898件を表すmodel配列の件数とは分ける。per-pageのfile writeは計測対象の挙動を変えるため行わない。

経過時間には`ProcessInfo.processInfo.systemUptime`を使うため、app targetの`PrivacyInfo.xcprivacy`へ`NSPrivacyAccessedAPICategorySystemBootTime`／`35F9.1`を申告する。これはapp内の処理時間だけを測り、外部送信や端末識別へ使わない。Archive Privacy Reportでも理由申告を確認する。

## 実機ゲート

Build 10で写真ブラウザが固まる場合は待機せず、後続buildを同じ端末へ入れて確認する。後続buildのアルバムgridから任意の写真を選べる状態で、実データ約898件の先頭付近、中間付近、末尾付近をそれぞれcold状態から5回開く。

- `page_count`が約898で、`requested_page_position`と500ms後の`settled_page_position`が一致する。要求位置だけから成功を推測しない
- `page_model_prepare_ms`は中央値16ms以下、全run 50ms未満
- `construction_to_appear_ms`は中央値100ms未満、全run 250ms未満
- `constructed_pages_500ms`は10以下を期待し、11〜50は要調査、50超はFAIL
- `explicit_preheat_pages`は5以下。端では通常3以下
- Xcode Hangsでopen時に250ms以上main run loopがbusyにならない
- navigation transitionが直ちに始まり、iCloud画像待ちの`ProgressView`中も操作できる
- 20〜50pageを連続で送り、指追従、慣性、snap、端のbounce、白画面なしを確認する
- 10秒idle後のmemoryが最初のsettle後から直線的に増え続けない。20MB超のretained増加、memory warning、terminationは要調査

1600px画像を最大5件preheatしても、`PHCachingImageManager`の内部保持量は公開契約で固定されない。件数上限だけを安全証明にせず、実機のMemoryとAnimation Hitchesを併記する。

Build 10には任意の先頭／中間／末尾を直接選ぶアルバムgridがないため、存在しない操作手順を要求しない。ホームの写真、Widgetの写真、利用可能なら「これ好き」の写真という既存の入口からcold状態で写真ブラウザを開き、約898件を渡した初期表示が固まらず、左右の写真が白く残らず、端でloopしないことを目視確認する。これは旧`TabView(.page)`の公開されていない初期化範囲や実体化件数を証明する計測ではなく、Build 10の操作上の合否だけを判定する。固まった場合は同じ端末へ後続buildを直ちに入れる。先頭／中間／末尾の反復と上記の数値gateは、任意写真を選べるアルバムと遅延pagingを含む後続buildで行う。
