# 共有設計

最終更新 2026-08-20

「共有」の構造をここに集約する。**実装前に確定させる必要がある内容。**
サーバー設計の分岐（製品構造.md 7章のA/B/C）は、ここで **D案** に確定した。

> **後続判断:** この文書の「自分の窓」「家族の窓」「履歴」は、2026-08-20時点の構想を追えるため残す。現在の画面と共有空間の用語、無料の「しおり」の保持境界、有料の長期保管を未実装とする判断は[ADR-019](ADR-019-しおりと長期保管.md)が優先する。

## 0. 用語

**窓 = 共有空間。人が窓に入る。**

ウィジェットは窓を覗く場所であって、窓そのものではない。
**1ウィジェット = 1つの窓。混ぜない。**

---

## 1. 共有の4パターン

| | 構成 | 誰が送れるか | 例 |
|---|---|---|---|
| ① 一人 | A → Aの窓 | — （サーバーを使わない） | いまのBuild 18 |
| ② 二人 | A ⇄ 窓 ⇄ B | 両方 | 夫婦 |
| ③ 三人以上 | A・B・C ⇄ 窓 | 全員 | 夫婦＋実家 |
| ④ 一方向 | A → 窓 → B・C | **Aだけ** | 保護猫団体、猫カフェ |

### ①一人

**共有機能を作っても、一人で使う人はこのまま動く。** サーバーを一切使わない。
「一人で使っている状態が、欠けた状態に見えてはいけない」の実装上の担保。

### ②③双方向

招待リンクで窓に入る。誰かが送ると、窓にいる全員の窓に出る。
**同じ写真が二人に出ることが価値。**

### ④一方向

- **BとCはお互いの存在を知らない**
- **Aも、BとCが誰かを知らない**（購読者数だけ）
- 返信も反応の内容も送れない（数だけ返る）

---

## 2. ★ 双方向と一方向は別のシステム

| | 家族の窓（②③） | 団体の窓（④） |
|---|---|---|
| 暗号化 | **E2E** | **しない**（公開配信） |
| 配送 | 1対1で暗号化コピー | **1オブジェクトをN人が読む** |
| 保持 | 期限付き | 団体が消すまで |
| 課金 | 個人が払う | 団体が払う（別プラン） |

**団体が1,000人に配信するのに暗号化コピーを1,000個作るのは成立しない。**

→ **団体の窓はv2。** v1は家族の窓だけを作る。

---

## 3. 窓の数

| | 無料 | 有料 |
|---|---|---|
| 家族の窓（双方向） | **1つ** | 複数 |
| 団体の窓（受け取るだけ） | 制限なし | 制限なし |

家族の窓を複数持てるのが課金軸のひとつ（夫婦だけの窓／実家も入る窓を分けたい需要）。
団体の窓は増えてほしいので制限しない。

---

## 4. 肉球（好き）の意味

**押す動作は1つ。起きることが窓によって違う。**

| 押した場所 | 好きに入るか | 送り主に届くか | 本に入るか |
|---|---|---|---|
| 自分の窓 | ○ | — | ○ |
| 家族の窓 | ○ | **○** | ○ |
| 団体の窓 | ✕ | 数だけ届く | **✕** |

**団体の猫が自分の本に入るのはおかしいので、そこだけ切る。**

### 出口

**本が出口。** 「あと◯枚で1冊になります」が肉球の意味を作る。
**これがないと押す理由がない。** 優先度は極めて高く、実装コストは極小。

### 本は個人ごと

Aが送った写真にBが押したら、**Bの本**に入る。Aの本には入らない。
**家族共通の本はv2。**

## 5. 送る先の切り分け

**切り分けが必要な人はほとんどいない。**

```
団体の窓　→　受け取り専用。送れない
家族の窓　→　無料は1つ
　　　　　　　＝ 送る先が1つ ＝ 選ばなくていい
```

選択が発生するのは **有料で家族の窓を複数持った人だけ。**
複雑さは払った人だけが背負う。

### 過去の写真は自動で家族に流れない

**送ったものだけが家族の窓に入る。**

理由：猫の写真でも、背景に人が写る／部屋が散らかっている。
**自動で家族に送るのは危険。**

例外として、窓の初期化時に各送信者へ **「毎日1枚、自動で送りますか」** を明示的に選ばせる。
**既定はOFF。** OFFのままなら過去写真を自動送信しない。ONを選んだ窓だけ1日1枚を自動送信し、
設定からいつでも停止できる。

### 立ち上がりの初期化

窓を作るとき、**アプリが20枚選んで見せて「これを送りますか」で一括OK。**

- 選ばせるのではなく、**確認してもらうだけ**（「設定を1回お願いするのはいい。キュレーションをお願いするのは駄目」の範囲内）
- これで最初から窓が埋まる（1日目に1枚しかない問題の解決）
- コストはペアあたり20枚が1回だけ
- **1つの窓につき1回だけ、通常の1日5枚とは別枠。** Serverが消費済みgrantを記録し、
  同じ窓のreset・再招待・作り直しでは再付与しない。途中失敗は同じidempotentな初期化を再開する

## 6. サーバー設計 ＝ D案（確定）

**期限付き・容量上限付きの暗号化配送箱。**
オリジナルを預からない。無期限保持をしない。

| 項目 | 内容 |
|---|---|
| 画像 | 長辺2048px／EXIF・GPS・ファイル名を削除／平均500〜700KB／暗号文1MiB上限 |
| 単位 | 1送信 = 1つの不変オブジェクト（**追記のみ。再発行しない**） |
| 暗号化 | E2E。写真ごとの鍵を、窓の世代鍵で包む |
| 流れ | reserve → R2にPUT → commit → APNs通知 → 受信memberごとに復号・ローカル保存・ACK |
| 削除 | 受領後7日／未受領30日 |
| D1に持つもの | ID・窓・memory\|live・時刻・サイズ・ハッシュ・期限・鍵世代・状態のみ |
| **持たないもの** | 写真本体・EXIF・GPS・PhotoKitのID |

画像から削除した撮影日時は、**認証付き暗号化payloadの中に入れる。** Serverは読めない。
受信端末は、Widgetの巡回順、年齢アルバム、PDFの撮影日順にこの日時を使う。
撮影日時がない写真は欠損として扱い、upload時刻で置き換えない。

3人以上の窓では、commit時の受信member集合を固定し、ACKと取得期限を受信memberごとに持つ。
最初の一人がACKしても、まだ受け取っていないmemberの30日枠を短縮しない。R2暗号文は全受信memberの
個別期限が終了または失効してから削除する。後から窓へ加わったmemberへ過去写真を自動公開しない。

### ★ 現行設計をそのまま使ってはいけない

**「毎日20枚を丸ごと再発行する」設計は月630万PUTになり、月$80〜245。**
D1の書き込み増幅を入れると、A相当でも下限が月$118。

→ **追記のみに変える。**
→ **過去写真の配送も「毎日20枚」ではなく「1日1枚」。受信端末がローカルに溜める。**

| | 見積（1万人・1日1枚） |
|---|---|
| A 現行設計 | 保存だけなら月$7だが、**PUTを入れると月$118〜245** |
| B オリジナル無期限 | 12ヶ月目に月$167／初年度累計 約$1,030。**採用しない** |
| C 中間 | 月$13〜15 |
| **D（採用）** | **月$9〜11** |

### 無料枠と有料枠

| | 無料 | 有料 |
|---|---|---|
| 送信 | 1日5枚 | 1日20枚 |
| 履歴 | 受領後7日でサーバーから削除 | 最長365日 |
| 家族の窓 | 1つ | 複数 |
| **画質** | **有料と同じ** | 同じ |

**画質を課金軸にしない。** 写真の見栄えは製品体験そのもの。無料版の写真が汚いのは製品の核を壊す。
課金は **送信数・履歴の長さ・窓の数** に置く。

**有料は後から追加する。** まず無料版だけを出し、送信頻度・返信率・窓の閲覧率を測る。

### 「バックアップではない」

有料の履歴は **「共有履歴365日」** と呼ぶ。**「バックアップ容量」と呼ばない。**

購入前の明示が必須：

> 共有履歴はバックアップではありません。保持期間を過ぎた写真は削除されます。
> すべての参加端末が鍵を失うと、保持期間内でも復元できません。

1台失っただけなら、残っている端末から復旧できる。**全端末を失うと不可。** v1でサーバーに鍵を預けない。

**B案が最も危険なのはここ。** StoreKitは購入を復元するが、暗号鍵は復元しない。
「無期限保存」を買った人が全端末を失うと、払ったのに何も戻らない。

## 7. Appleの制約

### UGC規定（Guideline 1.2）

**非公開の家族間の共有でも適用される。**

- 通報機能
- ブロック機能
- **公開の連絡先**
- **適時の対応義務**

**共有を入れると、サービス運営者になる。** 実装で終わらず、継続する義務。
**後付けだと審査で止まるので、共有と同時に実装する。**

### IAP必須（Guideline 3.1）

**送信枠・履歴はデジタル機能なので、IAP（15〜30%）が必要。**

```
物販（プリント・本）　　　→ Web決済でよい　　　3.6%
共有の送信枠・履歴　　　　→ IAP必須　　　　　　15〜30%
```

**→ 事業計画.md の「Web決済が単一最大のレバー」は物販にしか効かない。訂正が必要。**

### WidgetKit pushは保証されない

| | |
|---|---|
| iOS 26以上 | WidgetKit push で best effort |
| それ以前 | 通常通知は届く。**窓の更新は遅れる可能性** |
| 全OS | **「必ず数秒で出る」とは言えない** |

**訴求は「すぐ届く」ではなく「届いたら知らせる」。**

### プライバシー申告

**どの案でも「データを収集しません」は名乗れない。E2Eでも免除されない。**

App Functionality / User linked / Tracking なし で申告：
写真（暗号化プレビュー）／User ID（窓・メンバー）／**Device ID（APNs・Widget push token）**／Product Interaction／課金するなら Purchase History

## 8. 窓の表示ルール（過去と現在を混ぜない）

1. 新しく届いた写真を **2〜4時間、または反応があるまで優先表示**
2. 「いま届いた」＋送り主を表示
3. 複数届いたら、最新1枚＋残り件数
4. 優先枠を過ぎたら共有履歴に移す
5. 届いた写真がなければ、過去の写真を巡回
6. **「届いた写真を優先」の設定を用意する**

## 9. 前の判断からの変更

| 項目 | 前 | いま | 理由 |
|---|---|---|---|
| APNs | **入れない** | **入れる** | 即時性が価値になった（燃料の枯渇） |
| 過去写真の配送 | 毎日20枚を再発行 | **1日1枚。追記のみ** | 再発行が月$80〜245の主因 |
| 画質 | 課金軸にする | **しない** | 写真の見栄えは製品体験そのもの |
| 無期限保持 | 検討対象 | **提供しない** | 鍵を失うと復元不可。バックアップに見える |
| Web決済 | 単一最大のレバー | **物販のみ** | デジタル機能はIAP必須 |
| モデレーション | 身内だけなので不要 | **必要** | Guideline 1.2は非公開pairにも適用 |
| 団体の窓 | v1で検討 | **v2** | 双方向と別システム |

**ADR-009（毎日20枚／APNsを使わない／鍵の復旧なし）は新しいADRで置き換える。**
