# N28 / N29：家族の記録の契約案

2026-09-18。参照 HEAD `1d92f80`。設計監査のみ。以下の「推奨」は未採用・未実装で、販売・長期保管・復元の提供開始を意味しない。

目的は、各端末で本人が選んだ猫の写真と言葉が、一つの共同記録へ育つこと。個人のお気に入り・メモの自動共有は行わず、一人利用と猫登録任意を維持する。方針は [ADR-026](../NekoWidget/docs/ADR-026-うちの子との時間と会員体験.md)、既存境界は [共有まどの整理](2026-09-15-shared-favorites-concept.md) に従う。

## 推奨する具体的契約

1. **一つの共有先を一つの記録にする。** 初版は既存の検証済み私的まどの参加者範囲を再利用し、別まど・公式・端末全体の写真を混ぜない。`recordSpaceID`を記録の安定IDとし、配送spaceとの対応を明示する。表示名や支払者の変更で別記録にならない。将来の複数人対応と、現在の相手一人とのまどを混同しない。

2. **写真と言葉の著者を分ける。** 写真投稿は`entryID / authorParticipantID / mediaID / capturedAt? / addedAt / revision / state`。追記は`contributionID / entryID / authorParticipantID / text / writtenAt / updatedAt / revision / state`。各人は自分の写真・言葉だけを編集し、他人の本文を書き換えない。各追記は500字以内を出発点とする。同時編集はrevision不一致で入力を保持し、再試行IDで二重追加を防ぐ。投稿者は確認済み参加者identityで決め、名前・端末IDで推定しない。名前・猫名・本文・撮影日は現行と同じく暗号化対象にする。

3. **共有は確認した一回のコピー。** 写真・共有先・付ける言葉を確定してから追加する。個人メモの本文は既定で空、本人が明示して選んだ場合だけ共有用draftへコピーする。その後の個人メモ編集・削除・お気に入り解除は共有記録へ伝播しない。共有先や所属が変わった古いdraftは送信せず、再確認する。個人のPhotoKit ID・メモUUID・ローカルパスは端末内対応表にだけ置く。

4. **削除を三つに分ける。** 自分だけ非表示は他者に影響しない。著者の取り下げは共同集合からその写真／言葉を削除し、本文や画像を含まない削除記録を同期する。写真が取り下げられても他人が書いた言葉は勝手に消さず、写真なしの記録として著者を保つ。管理者は安全上、投稿を全体から非表示にできるが、他人の文章編集はできない。既に明示保存された個人コピーは独立して残る。オフライン端末には次回接続まで反映できず、全端末から即時回収とは約束しない。

5. **退出・blockは新しいアクセスを止める。** 通常退出前は任意の持ち出しを用意し、退出自体を保存完了で妨げない。既に投稿した内容は共同記録に残ることを追加時・退出時に明示し、自分の投稿を先に取り下げる選択肢を用意する。block／強制退出は即時に以後のアクセスを失効させ、共有表示cache・送信待ちを無効化する。鍵更新後の内容を旧参加者へ出さず、以前渡した内容や鍵の回収は保証しない。管理者が去る場合は管理権の引継ぎか記録の終了を別操作にする。**支払者・管理者・著者の権限を一体化しない。**

6. **猫所属は家族内の明示的な名札。** `sharedCatID`と各端末の猫プロフィールを本人が対応付ける。名前一致・顔認識・ファイル一致で自動統合しない。猫未指定・複数猫の写真を許し、登録を追加条件にしない。所属を変更できるのは写真投稿者。猫名の管理は管理者、既存記録の名前snapshotは保持する。猫プロフィール削除は写真と言葉の削除にしない。

7. **保存の種類をデータで区別する。** `displayCopy`（鑑賞用JPEG）、`originalBundle`（原本一式）、`referenceOnly`（所在参照）を分け、初期試作は`displayCopy`だけ。猫名・写真の見た目から欠けた画像を補わず、原本のPhotos削除と共同コピーの取り下げを連動させない。Live Photo・動画・編集履歴を扱わない段階で「原本保存」「完全復元」と表示しない。

8. **復元は個人の持ち出しと共有への復帰を分ける。** 共同データの復元対象は、著者・猫の共有ID・日付・言葉・共有コピー・更新／削除記録・書式版。通常の持ち出しは書き出し専用IDと名前で関係を保ち、内部参加者IDや認証・復号鍵を出さない。共有IDを保つ復旧snapshotと鍵の引継ぎは、別の保護された経路として設計する。取得したファイルの完全性を検証し、破損を別写真で埋めない。旧snapshotだけでは現在の参加資格や削除を判断できないため、共有へ再公開する前に最新の参加状態と削除記録を照合する。照合できない場合は共同記録に戻さない。個人の持ち出しコピーを読むことは、再参加や再共有の許可にしない。機種変更には写真だけでなく参加者identityと復号鍵の復旧が必要で、現行の端末追加だけを全履歴復元と呼ばない。

## N29から先に固定すべき約束

- 課金失効で過去記録を突然隠したり削除したりしない。容量上限は古い記録の自動間引きより新規追加の停止を優先し、閲覧・持ち出しを維持する。招待家族の既存共有先への追加に別契約を要求しない。
- 恒久保存の開始前に、暗号化blob・複製・転送・削除記録を含む原価と、解約／終了後の保持期間、告知・持ち出し期間、データ／鍵の復旧方式を確定する。期間や容量は未確定のまま販売しない。
- サービス終了時は利用可能な共有コピーと言葉を標準形式で持ち出せることを目標にする。PhotoKitの原本一式や、既に配送期限を過ぎた写真まで復元対象へ含めない。

## 次の実装単位は一つ：N28a「著者別の共同記録を二端末fixtureで往復する」

既存配送には接続せず、独立した記録モデル・権限判定・保存と、同じfixture上の二端末を使う。Aが写真＋一言、Bが自分の言葉を追記し、再起動後も著者別に読めるところまで縦に通す。続けて**同時編集の拒否、Aの写真取り下げ後にBの言葉が残ること、退出後の送信拒否、旧snapshotから取り下げ済み写真や資格が復活しないこと**を同じケースで確認する。未指定猫・写真欠損も本文が残る形で扱う。

合格は共同記録の契約検証であり、一般利用者へ長期保存を提供した扱いにはしない。その結果をもって、既存暗号化／参加者基盤を使った共通catalog・再取得の実装とN29の容量／復元設計へ進む。新server・deploy・課金・Widget選定・既存配送の保存期限はこの単位で変更しない。
