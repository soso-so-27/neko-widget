# 写真から、その猫のまどへ

2026-09-13。ユーザーの「まだアプリを開発したい」「進めて」を受け、LP掲載合わせを保留し、合意済みの公開まど第4段階を進める。

## 今回の範囲

- 公開写真の下の「この猫のまど」から内容を確認し、既存の「このまどを受け取る」で追加する。戻ると元の写真へ戻れる。
- 最初は「キジ白のまど」1つ。`cat-tabby-nap` → `generated-tabby-nap` の明示的な対応を使う。現在承認済みのAI画像 `generated-20260913-tabby-nap` が対象。同名のキジ白 `generated-tabby-v3` は別の猫IDであり混ぜない。
- 元の「どこかの猫」や「おひるね」の購読、配置済みWidgetの表示元を勝手に変更しない。猫のまども個別に停止できる。
- 登録されていない猫には使えない入口を出さず、猫のまど内には同じまどへのリンクを重ねない。
- 写真主体の表示、拡大、短いひとこと、提供元のAI表記を維持。私的共有のハートは変更しない。

## 完了条件と検証

1. 元の写真 → 猫のまど → 受け取り → そのまどのWidget案内 → 元の写真、が通る。購読先と戻り先をUIテストで確認。
2. 最大文字設定でも入口・写真・停止に進める。猫のまどの停止が元の購読へ波及しない。
3. 猫IDの不一致をプレビュー、取得、保存済み状態、画像読み出しで拒否し、Widgetも同じ保存境界を通る。期限切れでも購読意思は保持する。
4. 配信bundleは既存まど・履歴・休止を引き継ぐ。初回写真の掲載日・期限・hash・提供元を変えずに参照し、新規掲載と偽らない。将来の猫窓への追加も同じ猫IDに限定する。
5. 対象のローカル検証・独立レビュー → 候補CIを1回 → main → 既存の内部TestFlight。Appleアップロード成功を配布作業の証拠にし、毎回のASC画面照合はしない。

実装・検証・配信・実機を区別する。着手時点ではCI、preview配信への反映、TestFlightは未実施。下記に実測結果を追記する。

## 今回含めないこと

投稿受付、猫の自動識別、課金、新しいSNSや公開ハート、一般公開は含まない。この猫の継続供給用の新画像は今回生成しない。現在の1枚の掲載期限は9月20日16:42 JSTで、供給不足の際に別猫を代わりに出さない。

## 運用の引き継ぎ

手動配備も既存 `output/runtime/pending.json` の排他と配備前後のversion/HTTP照合を使う。配備後は固定保守checkoutのツールと `current.json` を引き継ぐ。旧2まどだけのbundleへ定期保守が戻さないよう、猫のまどを含むbundle・制約付き履歴を新しい基点にする。
