# 選んだ写真が集まる共有まど

2026-09-15。設計検討のみ・製品未実装。参照checkout: `96279fe`＋今回の階層短縮 `fe085ef`。現行コードと公式資料を確認した。今回作った配置案はブラウザ内の試作であり、実機の完成画面ではない。以下の価値・見せ方・使いやすさは仮説であり、fixtureや提供スクリーンショットの写真から選定品質を判断していない。

## 推奨する価値と見せ方

「あなたと相手が、それぞれ選んだ猫の写真を、同じまどで眺める」を共有まどの価値仮説にする。「お気に入り」は人が気に入って選ぶという意味にとどめ、端末の写真アプリの「お気に入り」やアプリの「思い出」を自動公開する意味にはしない。

既存の「まど」から相手のまどを開くと、最初に写真が並ぶ。現在の「届いた／送った」を主入口にする構成から、送受信の写真を同じ一覧で眺められる構成へ寄せる。新しい必須タブは作らない。「一か所」はまず**その相手とのまど**であり、異なる相手の写真を全まど横断で混ぜることではない。

推奨する到達点は、**各自が選ぶ → 同じまどに残る → Widgetでまた出会う → 気が向いたらハートや新しい一枚**というつながり。相手の猫を受け取る楽しさに加えて、自分では撮れなかった表情が同じ場所へ積み重なる価値を作る。新しい投稿がない日も見返す理由になる。連続投稿・反応・相互投稿は要求しない。

- 写真中心の一覧＋控えめな「写真を選ぶ」。1枚を選ぶ→写真・まど名・任意のひとことを確認→「届ける」の現行同意境界を維持する。写真詳細や個人の思い出からも同じ確認へ入る。写真アプリのお気に入りは、将来の選択候補として使えても送信許可にはならない。
- 一覧は同じ大きさの写真を基本とし、送信者・時刻・状態を各サムネイルに重ねない。写真を直接開くと、誰が選んだかと日付を控えめに確認できる。主な並びはまどへ追加した日時。昔の写真を追加しても、撮影日順で奥に隠れない。撮影日と追加日は詳細で区別する。通知やハートで並びを変えず、閲覧中の位置を保持する。
- 通信中の写真は送った本人に控えめな進捗として扱い、「相手にも届いた」とは確認前に表示しない。詳しい送信控え・再試行は既存の送信状況へ。欠損写真を別写真に差し替えたり、古い端末にも全履歴があるように見せたりしない。
- 個人の「写真」「思い出」は従来どおり使える。まどに参加しない人へ接続を要求しない。受信写真を自分の思い出へ取り込む操作も本人が選ぶ。

## 「選ぶ」「ハート」「残す」は別の意思

| 操作 | 意味・見える範囲 |
|---|---|
| 写真を選んでまどへ届ける | この写真を、このまどの相手に見せる意思。別のまどや今後の写真の送信許可にはしない。 |
| ハートを送る | 届けてくれた相手への反応。現行の送信待ち・送信済みを維持し、個人のお気に入り登録や長期保存を兼ねさせない。 |
| 自分の思い出に残す | 本人の写真アプリへコピーし、個人の思い出へ登録する操作。相手への通知や共有ハートを発生させない。 |
| 共有コレクションに長く残す | 現行には独立した永続保存契約がない。必要になった場合だけ、保持と削除権限を決めて追加する。「ハートを押したから永久保存」とは解釈しない。 |

「二人のお気に入り」という名前は双方が選定に同意したように見えるため初期名称にはしない。まど名と「まどの写真」で十分。ハート数によるランキングや二重のお気に入り設定も初段階には不要。

統合一覧はローカルではまどの検証済みcontext＋写真の安定IDをキーにし、受信・送信で同じ写真を二重掲載しない対応が必要。見た目の類似や同じファイルhashだけで、異なるまどの所属・削除権限を合併しない。「あなた」は送信方向だけから判定せず、同じ人の別端末も含めて確認済み参加者identityに基づける。追加端末の参加は既存の明示的な追加・復旧経路を維持する。

## Widgetとのつながり（提案・未実装）

- 新しく追加された写真があるときは、それを優先。新着がない日は、そのまどに集まった過去の一枚を見返す案。頻繁にランダムで飛び変わる設計にせず、日単位を出発点にする。頻度・同じ写真を選ぶ範囲は採用前に決める。
- 写真タップは対象写真へ直接。相手の写真には今あるハートを残し、ハートのためにアプリを開かせない。自分の写真へ自分から反応するボタンは出さない。
- 現行のハート送信には写真の `accessExpiresAt` と共有権限が必要。期限を過ぎた写真を長期保持しても、既存の送信経路だけで反応し続けられるわけではない。過去の写真にもハートを送れる到達点にするなら、保持契約とともに権限・反応の期限を追加設計する。古いキャッシュのボタンだけを有効にしない。
- 共通なのは写真の集合。表示中の一枚や反映時刻が双方で常に一致するとは約束しない。iOSの更新機会に左右されるため、アプリ側で見える最新情報とWidgetの実表示を区別する。[Appleの更新仕様](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date)
- 個人の猫写真Widget、公式・お題・猫別まどとは別の共有まどの選定規則にする。複数の相手の写真や公開写真を混ぜない。

## 実装へ進むならこの順

1. **具体案を確認**：一つのまどへ双方が選んだ写真が集まる一覧と、そこからのWidget再発見を、今回の画面案で比較する。送受信タブを消すこと自体が目的ではなく、同じ写真を眺められるかを確認する。
2. **保存の契約を決める**：共有コピーを、取り下げやまど終了など定義した条件まで残す。容量上限・運用費・終了時の扱いを先に定め、容量到達で大事な古い写真を黙って消さない。端末にある原本を移動・削除する方式は採らない。
3. **一つのまどの保存・再取得と一覧を実装**：安定した写真catalog、参加者の権限、再取得、端末追加、削除通知を扱う。現行の手選び・宛先確認・ハート・個人保存・送信状況は再利用する。配送cacheの日数を伸ばすだけでは完成としない。
4. **Widgetの再発見を接続**：新着・新着なし・写真取り下げ時に、そのまどの実在する写真を指す。最後に両端末で追加・再起動後の見返し・Widgetから直接開く・取り下げをまとめて確認する。

今の端末内cacheを一つの一覧にまとめるだけでも配置は試せる。ただし、それは一時的な試作であり、ユーザーが感じた「写真が一か所に積み重なる価値」の完成形にはしない。

低コストな代替は、現行の受信写真を「自分の思い出に取り込む」入口と出所の分かりやすさを改善すること。「自分の手元の一か所に集まる」は早く試せるが、双方が常に同じ集合を見る体験にはならない。まど別に取り込み済み写真を長く絞り込むなら、現在の受信履歴が消えても残る個人用の出所記録が別途必要であり、共有情報をどこまで残すかを決める。

もう一つの代替である全ライブラリ同期は、本アプリの手選び・一人利用・小さなまどという範囲を超える。写真や端末のお気に入りを無断で自動送信する案は採らない。

## 実装前に決める保存・削除の境界

| 決める境界 | 推奨する初期方針 |
|---|---|
| まどの表示履歴と長期保存 | 現行の期限付き表示と、本人がPhotosへ保存したコピーを分ける。長期共有保存は保持期間・容量・費用・移行を決めるまで約束しない。 |
| 自分の思い出から外す | 個人の登録だけを外し、Photosコピーや相手の写真は削除しない。現行意味を維持する。 |
| まどから写真を削除する | 「自分にだけ非表示」「自分の投稿を共有から取り下げ」「相手の保存済みコピー」を区別する。将来の共通一覧の取り下げ権限は未決定。現行の受信削除を全員からの撤回と読み替えない。 |
| 共有終了・block | 新しい共有と一時的な表示を停止する。既に明示保存したPhotosコピーは残り、送信者から回収できない。通常の終了前に任意保存へ戻れる導線は検討できるが、blockを保存作業で遅延させない。終了後の一括救出は権限と現行削除処理から自動的には提供できない。 |
| 別端末・再インストール | 共有参加の復旧と、Photosコピーの同期は別の仕組み。未保持の過去写真が自動復元するような案内をしない。 |
| 片側だけ未着・期限切れ・原本削除 | 残っている別写真で穴を埋めず、その写真の状態を示す。相手端末の写真削除を、本人の保存済みコピーへ自動伝播させない。 |

## 公式事例からの示唆（取得日はいずれも2026-09-15）

- **Apple iCloud共有写真ライブラリ**：追加した写真は共有ライブラリへ移り、参加者が編集・削除できる。お気に入り変更も共有される。共有集合そのものを共同管理するモデルであり、個人の保存と相手への反応を分ける本案とは契約が異なる。[概要](https://support.apple.com/en-us/118229)、[共有される変更](https://support.apple.com/en-in/guide/iphone/iph1a6c849ab/ios)。
- **Apple共有アルバム**：写真を選び、アルバムを指定して投稿する。共有画像はコピーで、保存した個人ライブラリの写真は共有アルバム削除後も残る。写真は長辺2048px等の制約があり、集まって見えることと原本保管は同じではない。手選び・出所・個人保存の境界が参考になる。[公式説明](https://support.apple.com/en-us/108314)。
- **Google Photos共有**：選択した写真を相手や共有アルバムへ送れ、投稿者とlikesが表示される。共有写真を自分のライブラリへ保存するとコピーになり、その後の元写真の編集は保存済みコピーへ反映されない。反応・共有所属・個人保存を別に理解できる表示が参考になる。[公式説明](https://support.google.com/photos/answer/6131416?co=GENIE.Platform%3DDesktop&hl=en)。
- **Google Photosパートナー共有**：保存済み写真は共有相手の削除・共有終了後も自分のライブラリに残る。一方、自動保存設定も持つ。保存済みコピーの独立性は参考にし、自動共有・自動保存を本案の既定にはしない。[公式説明](https://support.google.com/photos/answer/7378858?co=GENIE.Platform%3DiOS&hl=en)。

これらは競合の機能をそのまま移す根拠ではない。試すべき仮説は、送受信という操作分類より先に「同じ相手と選んだ写真」を見せると、まどを開く理由が明確になるか。判断には両端末で手選び→受取→見返し→個人保存を実際に使う観察が必要で、今回はそこまで確認していない。
