# 公式まど「どこかの猫」

2026-09-10、利用者の「公式窓作成してください」に基づく初期実装。

## 目的と今回の範囲

自分の猫写真や送る相手がいなくても、公開用に提供された猫写真をホーム画面で楽しめるようにする。最初は運営が選ぶ配信1つに、複数の提供者・猫の写真を載せられる構成。個別猫の公開まど、投稿者アカウント、推薦学習、公開ハート、チャット、課金は今回の範囲に入れない。既存の非公開まどのハートは変更しない。

アプリでは「まど」→「どこかの猫」→「このまどを受け取る」。共有が無効でも、公式の配信先を設定したビルドなら「まど」から公式まどに進める。共有も公式配信先もないローカル専用ビルドでは、従来どおり「まど」タブを出さない。写真権限、猫登録、連絡先、招待、投稿は不要。Widgetの「表示する写真」で「どこかの猫 · 公式まど」を選ぶと、写真1枚と小さな猫名を表示する。写真をタップするとその写真の詳細へ進み、全体・説明・提供者・撮影日（任意）を確認できる。アプリ内は縦横比を保持し、詳細は最大2048pxの配信JPEGを使う。

## 実装と配信開始の区別

- 初回は利用者自身の猫写真で表示・更新を試す方針を、2026-09-10に利用者が選択。対象の写真原本と猫の公開名はまだ未指定。過去の不具合確認用スクリーンショットは掲載写真に流用していない。
- `OFFICIAL_WINDOW_FEED_URL` は空。現状のアプリは「公式まどを準備しています」と表示し、受信したように装わず、購読ボタンやネットワーク通信を有効にしない。
- CIの確認画像は既存の合成fixture。実際に暮らす猫の新着写真・正式掲載写真として扱わない。
- 公開サーバーへの配備、外部公開、main統合、TestFlight配布、App Store提出、課金開始はこの実装とは別。
- 朝夕1枚ずつは議論上の頻度案。コードや紹介文で1日2回・定時更新を約束しない。

## 配信データ

配信データ生成は `official-window-tools/build_catalog.py`。公開を承認したローカル写真と提供者情報から、`catalog.json` とSHA-256名のJPEGを新しい出力ディレクトリへ生成する。詳細は同ディレクトリのREADME。

- 入力ごとの `publicationApproved: true` が必須。これは同意の実在を証明する仕組みではなく、運営側の提供許可の確認記録を前提とする。
- 最大60件。実在の猫を識別する `catID` と各写真の `id` は運営が割り当てる。写真解析による猫個体識別は使わない。
- EXIFの向きを反映し、最大2048px・JPEGへ再変換して元のメタデータを除く。1ファイル4 MiB超は失敗とする。空の説明は省略。
- `publishedAt` 以前の写真は出力しない。各写真は最大14日の掲載期限を持つ。catalog自体の有効期限は最大48時間。
- 写真ID、公開猫名、提供者の公開名、任意説明・撮影日、公開期間、JPEG寸法/hashだけを配信する。内部の許可記録や元ファイルパスは含めない。
- `--paused` は `enabled:false, photos:[]` のcatalogを生成する。
- 更新・停止の `generatedAt` は以前の版より新しくする。同じ秒で内容が異なる版を作らず、同時刻の競合や古い版で停止を巻き戻さない。

## 受け取り・停止の境界

- URLはビルドで指定する単一HTTPS catalog。認証・cookieなしのGETのみ。同じディレクトリのhash名JPEGだけを読み、リダイレクトを追わない。
- 非公開まどの配信サービスURL、暗号鍵、ユーザー写真、送信キュー、個人写真のキャッシュを流用しない。
- 受け取りを選ぶまでは取得しない。受け取り停止時は購読世代を変え、端末の対象JPEGを削除。停止後に遅れて完了した通信は保存できない。
- 停止catalogや写真の取り下げは、画像取得より先に端末の許可リストへ反映する。新しい画像の取得失敗で古い取り下げ写真を復活させない。
- 通信失敗時は有効期間内の確認済み写真だけを保持。新着確認ができたと偽らない。期限後は空のWidget entryへ切り替えるtimelineを作る。
- Widgetは通常1時間後の再取得を要求するが、実行・画面切替の時刻はiOSが決める。配信者の取り下げが全端末へ即時反映する保証はない。
- アプリで開いている詳細は、取り下げを取得したときに閉じる。通信がなくても30秒ごとの期限再評価で掲載終了した写真を非表示にする。

## 配信開始までに残ること

1. 最初の掲載写真・猫の公開名・提供者名・掲載許可を決める。毎月継続できる供給量を確認する。
2. 静的配信先は専用Cloudflare Worker + Static Assetsに決定。ローカルで差し替え・停止まで成功済み。実写真の版を作り、公開する段階で配備する。詳細は `OfficialWindowService/README.md`。
3. アプリとWidgetへ同じcatalog URLを設定する。非公開の共有機能のON/OFFとは独立した設定にする。
4. 実機で初回受信、Widget表示・写真タップ、受け取り停止を確認して、既に許可された配布範囲を判断する。

実装の完了と、写真を継続配信できる運営状態の成立を別々に記録する。

## 初回の写真確認バッチ

最初は利用者が指定する写真2枚で十分。1枚目で表示と詳細への遷移を確認し、2枚目へ差し替えて更新を確認する。提供者の表示名は初期案として「ねこのまど」を使い、指定があれば変更する。猫の名前は本人の指定を使い、写真から推測しない。

1. 原本を受け取り、掲載対象と猫の名前を記録する。元画像・入力JSON・内部記録はリポジトリ外で保持する。
2. 既存の生成ツールで配信用JPEGを作り、実写真の向き・色・画質を確認する。
3. 写真Aを配信する版と、写真Bへ更新する版を準備する。配信先の技術選定・設定は実装担当が行い、利用者にサービス選定を求めない。
4. 実機でWidgetの切り取りと猫名の配置、タップ先が表示中の写真と一致すること、写真Bへの更新、受け取り停止を確認する。iOSの更新時刻を定時保証として扱わない。

今回の目的は表示・更新の動作確認。「よその猫が届く楽しさ」や継続利用の価値まで確認済みとはしない。写真提供元の選択だけで、過去の全添付写真の利用や外部公開を承認したことにはしない。アプリコードは変更せず、成功済みCIも繰り返さない。

## 写真を待たずに進めた配信準備

利用者の「すすめてください、いちいち止めないで」に基づき、写真未指定を理由に配信側の準備まで止めない方針へ変更。`OfficialWindowService/` を追加した。

- 専用Workerの配信コードと配備設定を作成。Cloudflareアカウントの既存CLIログインも確認。非公開まどのサービスやストレージへ接続しない。
- 明確に合成テスト画像と表示したA/Bのcatalogを既存publisherで作るツールを追加。実在の猫や提供者の写真を装わず、以前の添付写真は使わない。
- catalogと対応JPEGだけを配備パッケージへまとめる。原本・入力JSON・余計なファイルを公開フォルダーに含めない。既存出力は上書きしない。
- 同じローカルURLでA → Bへの更新 → 停止を、実Workersランタイムで確認。停止後のA/B画像URLは404。期限またぎの指摘を独立レビューで受け、返答直前の再評価と対象テストを追加。
- Node 14件、fixture生成5件、実HTTPの更新・停止、配備dry-runが成功。公開・実アップロード・TestFlight配布は行っていない。
- 証拠は `C:/dev/neko-widget-official-local-proof-20260910/http-drill-final/result.json` と `deploy-dry-run-final.log`。元のiOSコードやworkflowを変更していないため、全iOS CIを再実行しない。

実際の猫写真への差し替え、公開先での取得、実機Widgetの見え方は未確認として残す。外部公開・審査提出・課金開始をまだ行わないという既存の依頼は維持する。
