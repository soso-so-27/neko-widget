# 写真に付くメモを一つの体験にする

2026-09-20。状態：設計。アプリ・CloudKit・既存データは変更していない。
基点：origin/main `78149b95591b56726f1e4841acb5b5dd1b03a5b8`（製品Build192）。

## 目的

写真を見て「このときのことを書こう」と思ったら、その写真にメモを書ける。後日、同じ写真とメモを開き、同じ場所から直せる。利用者が「端末メモ」「保管した記録」の違いを学ぶ必要をなくす。

利用者に見せる概念は、写真、お気に入り、メモ。iCloudは保管先として扱う。メモ作成・保管だけで課金価値が成立したとは判断しない。

## 確認した問題

利用者提供画面では、同じ「メモあり」から「記録」と「思い出のメモ」に分岐し、写真の大きさ・編集位置・日付・タイトルが異なる。入口をまとめても、読み返しと編集は統一されていなかった。

現行には、個別写真の鉛筆と、設定の「写真と言葉を選ぶ」という二つの作成方式がある。前者は端末メモ、後者は独立した保管コピーを作る。送信時の「ひとこと」は相手に送る文章であり、個人メモとは別。

## 決める構成

| 場所 | 役割・操作 |
| --- | --- |
| 写真タブ：すべて | 写真を探し、開く。鉛筆からメモを作成・編集する |
| 写真タブ：お気に入り | 気に入った写真を絞り込む。ここから開いても同じ個別写真画面 |
| 写真タブ：メモあり | メモのある写真を、本文と写真の一覧で読み返す。削除しない |
| アルバム・本人の写真Widget | 開いた写真に同じ鉛筆を置く。入口が違っても同じメモへ進む |
| 設定：iCloudの保管と復元 | 保管状況、問題の対応、復元を扱う。写真を選んで文章を書く機能は置かない |

ホームタブ、独立したメモ作成ページ、アルバムのお気に入りアイコンは追加しない。メモを書く経路が複数あっても、作成方法・編集画面・保存する内容は一つにする。

## 画面と文言

### 個別写真

- 上部は戻る・鉛筆・その他。写真だけの場合もメモ付きの場合も、位置と大きさを合わせる。
- 拡大・写真送り・お気に入り・送信は、写真の種類と既存の利用権限に応じて維持する。今回の見本はメモの表示・編集部分に範囲を絞っている。
- 主役は大きな写真。その下にメモ、補足の日付。写真タップで拡大する。小さなサムネイルから「写真を見る」を経由させない。
- 「記録」「思い出のメモ」という保存方式別のタイトルは使わない。通常の個別写真と同じ構造にする。
- 鉛筆は常に同じ場所。読み上げは未作成なら「メモを書く」、既存なら「メモを編集」。空の本文枠は常設しない。
- 撮影日が分かる場合は撮影日。不明なら「メモ 9月19日」など、実際に分かる日付を示す。保管日を撮影日に置き換えない。更新・保管時刻は詳細へ。
- 通常画面には毎回「iCloudに保管済み」「保管した記録」を並べない。保管処理中・未完了は、利用者に必要な場面で短く表示する。

### 編集

写真の鉛筆 → 写真の小さなプレビューと入力欄 → 保存 → 元の個別写真。タイトルは「メモ」。閉じる際に未保存の変更があれば破棄を確認する。作成も編集も同じ画面。

初回の編集でだけ「自分だけのメモです」を補足する。相手に送る操作とは接続しない。500文字などの既存入力制約はデータ契約を確認して継承し、入力開始前から制約説明を大量に出さない。

### メモあり一覧

写真・本文・日付・進む印の並びと大きさを揃える。保管場所による行の差をなくす。本文で選んで、その写真を一度で開ける。検索と一覧位置を維持する。新規作成のための別のプラスは足さない。

## 保管は二つ目のメモを作らない

最終形は、一つの論理的なメモに端末とiCloudの保存先が付く構造とする。

1. 書いて保存すると、まずこのiPhoneに保存する。書いただけではアップロードしない。
2. 保管したい写真で「… → iCloudに保管」を選ぶ。
3. 初回に、この写真の閲覧用コピーとメモを保管し、以後のメモ変更も反映することを説明して開始する。原本のバックアップとは呼ばない。
4. 以後は同じ鉛筆から編集。端末へ保存後、保管済みの同じ記録へ変更を反映する。元メモとコピーを別々に選んで編集させない。
5. 通信が使えない場合も端末の編集を失わない。「このiPhoneに保存済み。iCloudへの反映待ち」を保管状況に表示する。クラウド反映を確認する前に「保管済み」としない。

写真ごとの明示操作を初期範囲とする。全写真・過去メモを自動でアップロードする設定は今回追加しない。既存の保管コピーを新方式に移す際も、新しい自動反映の意味を説明し、利用者が有効にするまでは現状の内容を保持する。

「メモを削除」は文章を消す操作で、写真やお気に入りを消さない。保管対象なら保管先の文章にも反映する範囲を確認文に示す。「iCloudからこの写真の保管を削除」は保管管理の別操作とし、このiPhoneに残るもの・失われるものを明記する。既存の記録削除APIへ同名ボタンを付けるだけでは実現できない。

## 他の機能との境界

| 機能 | 利用者がしたいこと | 対象 |
| --- | --- | --- |
| お気に入り | この写真をすぐ見つけたい | 写真の目印 |
| メモ | このときの出来事を覚えておきたい | 自分用の文章 |
| 送信時のひとこと | 相手にこの気持ちを伝えたい | 選んだ写真と一緒に相手へ送る文章 |
| iCloudに保管 | 選んだ写真とメモを別のiPhoneでも取り戻したい | 明示的に選んだ写真のコピーとメモ |

メモを送信時のひとことへ自動で入れない。ひとことから個人メモも自動生成しない。共同記録の公開範囲はこの個人メモ統一によって変更しない。

## 既存データを守る実装契約

現行保管は自動同期でも履歴保存でもない。同じ端末メモを保管し直すと、既存の保管IDを再利用して内容を更新する。メモID・版・PhotoKit IDとの対応は端末側にある。見た目の統一だけで自動反映を約束できない。

必要な変更：

- PhotoKitの端末内IDに依存しない共通IDを持つ。端末メモ・保管済み記録・写真参照を明示的な対応として結ぶ。クラウド復元後も同じ記録を編集する。
- 本文が一致し、信頼できる明示対応があるものだけ一つに表示する。題名、似た画像、近い日付から勝手に統合しない。
- 対応が不明な古い記録は独立したメモ付き写真として保持する。元写真が端末から消えていても保管コピーを表示し、本文を編集できるようにする。
- 同一記録の異なる変更は、端末時計による「新しい方」で黙って上書きしない。双方の内容を保持し、必要なときだけ「別の変更があります」から選べるようにする。
- 削除の版・反映待ち・再試行を扱い、復元で消した文章が無条件に復活しないようにする。アカウント変更時に別アカウントへ保管しない。
- 移行は再実行でき、途中失敗でも旧内容を失わない。変換成功前に旧保存先を消さない。過去の全文履歴や原本復元が存在するとは案内しない。

既存の別内容を無理に一つにすることは、画面をシンプルにすることとは別。例外の保護を通常時の二重編集にしない。

## 実装順と完了条件

1. **共通の表示と入口**：二つの提供例を同じ写真詳細・鉛筆・編集配置へ。設定の独立作成入口を削除。メモあり一覧を維持。既存データはまだ書き換えない。
2. **一つのメモとして扱う保存契約**：共通ID、旧データの明示対応、保管を選んだ記録の更新、競合・削除・アカウント境界を実装。保存場所で別編集になる状態を解消。
3. **対象を絞った確認と内部配布**：下記の代表操作と保存契約を確認。UIの変更と無関係な全画面操作は繰り返さない。最終修正候補から内部配布20〜30分を目標とし、超過時は原因を分けて報告する。

内部の段階実装はできるが、1だけで「体験統一が完了」としない。現在のスナップショット方式に自動反映の文言を先行させない。

完了条件：

- 写真・アルバム・本人のWidgetから同じ写真を開き、同じ鉛筆で一つのメモを作成・編集できる。
- 提供例二つが同じ配置で開き、編集・戻る・検索復帰ができる。余分な「写真を見る」がない。
- オフライン編集後も再入力不要。反映待ちと成功が正確で、同じ写真に不意に二つのメモが増えない。
- 既存の異なる文章、元写真がない記録、復元後の記録が失われない。競合・削除・アカウント変更をデータ層で確認する。
- 自分用メモが相手へ自動送信されず、書いただけでiCloudへ自動アップロードされない。

画面操作確認は代表2経路（通常写真からの作成／旧保管記録からの編集）と一覧への復帰を中心にする。データ競合などは画面を長時間操作する代わりに保存層のテストで確認する。本設計作業でCI・TestFlightは動かさない。

## 根拠と判断の限界

Appleの[Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles)は必要なものに絞ることと一貫した構造、[Writing](https://developer.apple.com/design/human-interface-guidelines/writing)は目的の明確さと一貫した用語、[Layout](https://developer.apple.com/design/human-interface-guidelines/layout)は階層と段階的な情報提示を重視する。この案の根拠に使ったが、Appleがこのデータ設計そのものを推奨しているという意味ではない。

主な実装根拠（この文書と同じcheckout）：

- `NekoWidget/NekoWidget/Views/LikedPhotosView.swift`：個別写真のpersonalNotePhotoとPhotoMemoryNoteEditor。
- `NekoWidget/NekoWidget/Views/PhotoMemoryNoteLibraryView.swift`：メモ一覧、個別メモ、保管入口。
- `NekoWidget/NekoWidget/Views/PersonalArchiveView.swift`：独立した作成・表示・言葉編集。
- `NekoWidget/NekoWidget/Views/SettingsView.swift`：iCloudの保管と復元。
- `NekoWidget/NekoWidget/Services/PersonalArchiveStore.swift`：明示リンク、重複表示判定、既存保管IDの更新。
- `NekoWidget/NekoWidget/Services/PhotoMemoryNoteStore.swift`：写真がなくても記録IDから編集できる契約。

保存契約は独立担当の読み取りレビュー結果を本書へ統合した。設計の分かりやすさは案であり、課金価値・別実端末での復元成功・競合解消成功の実証ではない。
