# 同じ1枚の画像形式比較（Build 7）

## ここまでの証拠

Build 6はAppleの処理完了・内部テスト中・本人用グループへの配布を確認済み（build UUID `328e9f02-f494-40f6-b114-51b731161cba`）。本人の入力診断v2では、1024×768の読み取り成功後、Vision revision 2が空の結果配列を返した（`resultsAvailable=true`、`observationCount=0`、`labels=[]`）。システム猫ラベルも`Cat`だった。今回はアプリの文字一致・0.5フィルターより前で0件であり、cropやONNXは未実行。以前の30枚の個体判定結果まで同じ原因と決めつけない。

本人は「元の写真」が写真アプリと同じ向きで表示されると確認した。そのサムネイルはVisionへ渡したラスタから作っているため、大きな回転・内容取り違えの可能性は下がる。ただし小さな表示だけで色空間、ピクセル形式、HDR等の正常性までは証明できない。コードの明確な向き補正漏れは見つかっていない。従来の8方向の合成確認を理由なく再実行しない。

## 比較の範囲

現在の`upright`は`UIGraphicsImageRenderer`で形式を明示していない。Appleはrendererのpixel formatをシステムが選ぶと説明しているが、それ自体は不具合ではなく、Vision失敗の原因とする証拠でもない。[Apple preferredRange](https://developer.apple.com/documentation/uikit/uigraphicsimagerendererformat/preferredrange)、[standardの色変換](https://developer.apple.com/documentation/uikit/uigraphicsimagerendererformat/range/standard)。

- 入力1枚の明示確認操作だけが対象。PhotoKitから取得した**同じラスタ**を使用する。
- 元の結果が「取得済み・候補0件」の場合だけ、同一寸法の8bpc/32bpp・opaque sRGBのCGContextへ1回再描画し、同じrevision 2・`Cat`/0.5で追加1回だけ検出する。
- 回転、拡大、中央切り抜き、明るさ調整、別モデル、別写真、再取得、バッチ診断の追加処理は行わない。
- 元の入力結果、crop、モデル実行結果はそのまま保持する。比較側で猫が見つかってもモデルへ渡さず、自動振り分けへ採用しない。
- 入力確認v3の`formatComparison`へ元/比較側の寸法・bit数・float有無・固定分類の色空間名、比較側の検出集計を出す。pixels、ICCデータ、写真ID、猫名、座標、特徴量は出さない。画像・比較結果を保存しない。
- 変換失敗、検出例外、未取得結果を「検出0件」と混同しない。処理間に取消を確認し、取消を失敗結果へ置換しない。
- 空の「猫の範囲」には「切り抜きなし」を表示する。検出できない状態を、画像表示バグと区別するための小変更に留める。

## 解釈と停止条件

- 比較側で候補が出た場合も、色変換・bit深度・ラスタの再生成のどれが効いたかは区別できず、根本原因の確定や個体識別精度の証明にはしない。
- 両方0件なら「この形式変換だけでは改善しない」と判断する。AppleのOS不具合、写真不良、モデル不良と断定しない。
- この1枚で閾値や前処理を繰り返し調整しない。結果を受けて、検出器の選択を進める価値があるか、本線と切り離して研究を保留するかを判断する。

## 最小検証

非正方形の合成画像で同じ寸法・角の色/向き・8bit sRGB出力を確認する。空結果だけの1回実行、変換/検出失敗、取消、比較成功時も元の失敗を保持するJSON境界を対象テストに含める。実写真の結果は本人からの診断を待ち、合成テストの成功を実写での改善と扱わない。
