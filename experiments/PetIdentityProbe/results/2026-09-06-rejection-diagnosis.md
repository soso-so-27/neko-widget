# 写真の再選択なしで行った保留原因の切り分け

対象: `c44bb89` / 専用検証アプリ Build 4。2026-09-06。
以下1〜4節はローカル調査時点の記録（本アプリ・モデル・判定基準変更、写真取得、モデル取得、依存追加、CI、push、TestFlight配布なし）。
その後ユーザーの継続依頼を受け、5節の限定的なApple環境実測を実施した。本アプリ・判定基準・main・TestFlightは変更していない。

## 結論と限界

- 元の Build 3 は correct 5 / wrong 0 / unknown 25（A: 0/0/15、B: 5/0/10）。登録10枚はすべて画像取得・猫crop・有効な特徴抽出を完了しないと集計へ到達しない。全面的な権限失敗・モデル起動失敗ではない。
- ただし評価25枚の unknown は、画像入力失敗と判定による棄却の両方を含み得る。旧集計に内訳や写真IDはなく、今回の直接原因・以前の選択は復元できない。
- 正解の猫に近い合成特徴でも、現在の判定式だけで同じ 5/0/25 を作れる。モデル精度不足と断定できない。
- 1024pxまでの全体縮小→猫cropという順序には、小さい猫の除外・細部損失の可能性がある。実写真への影響量は未測定。
- WindowsではAppleのCoreGraphics/UIKit/Visionを実行できない。今回のPillow実験をApple実装との画素一致検証に読み替えない。Swift・ONNXも今回実行していない。
- 自動振り分けの一般提供は引き続き保留。成功件数を増やすための閾値緩和は行わない。

## 1. 入力仕様の照合

コード: `Sources/IdentityPhotoService.swift:187–292`。

猫全体のbbox、224×224への直接resize、RGB/NCHW、ImageNet mean/std、512次元L2正規化という基本仕様は一致。顔だけに変更する根拠はない。

作者の推論コードはOpenCVのAREA/LINEAR、現実装はCoreGraphics `.high`。作者側の切り抜き最小辺2pxに対し、こちらは全体を最大1024pxへ縮小した後の最小辺32px。検出器も異なる。これは確定した仕様差であり、直ちにバグや実写真の保留原因を意味しない。32px基準を作者に合わせて2pxへ落とす提案ではない。

## 2. 切り抜きサイズと処理順序の合成確認

Python / NumPy 2.4.5 / Pillow 12.3.0。メモリ内で作った数値・図形のみ。写真も動物モデルも使用していない。

4096×3072の画像を1024×768へ縮小する例。bboxは整数境界に整列し、丸めの影響を除いた。

| 原本上の正方形領域 | 全体縮小後 | 現32px条件 | モデル入力 |

| 112×112 | 28×28 | 不成立 | 抽出せず |
| 128×128 | 32×32 | 成立 | 224×224 |
| 256×256 | 64×64 | 成立 | 224×224 |
| 896×896 | 224×224 | 成立 | 224×224 |

次に4096×3072の灰色画像の(1024,1024)へ256×256の合成パターンを配置。
同じPillow BILINEARで、次の処理順序だけを比較した。

- A: 原本上の256px領域をcrop→224pxへresize
- B: 全体を1024pxへresize→同じ領域64pxをcrop→224pxへresize

| 合成パターン | RGB絶対差平均（0–255） | RGB絶対差最大 |
|---|---:|---:|
| 滑らかなグラデーション | 1.161007 | 32 |

周波数の高い合成模様では縮小順序で大きな差が出る。これは細部が失われ得ることの確認であり、猫の毛柄・識別精度の実測ではない。周辺の灰色背景との補間も差へ含まれる。Appleの補間係数・色管理の一致は未確認。閾値境界と帯がグラデーションより大きい差になることのassert 2件を確認した。

## 3. 判定式だけによる同一集計の反例

コード: `Sources/IdentityEvaluationCore.swift:231–250, 319–345`。
距離は `1−clamp(dot,−1,1)`。クラスscoreは5見本への距離の2番目に小さい値。
登録半径は各見本を1つ除いたscoreの中央値。採用条件は `best <= 1.25 * radius` かつ `best/runnerUp <= .70`。

ソースの式をJavaScriptへ移し、メモリ内で計算した（Swift実行ではない）。
512次元の先頭2成分へFloat32の `cos(theta), sin(theta)`、残りを0に設定し、Double相当で再正規化。

| 項目 | A | B |
|---|---|---|
| 見本角度 | −.012, −.006, 0, .006, .012 | 1.38, 1.44, 1.50, 1.56, 1.62 |
| 登録半径 | 約0.00001799995 | 約0.00179946032 |
| 評価角度 | .080〜.094（.001刻み15件） | 1.580〜1.584（5件）＋1.700〜1.709（10件） |
| 結果 | correct0 / wrong0 / unknown15 | correct5 / wrong0 / unknown10 |

30件すべてが最小scoreでは正しい猫に対応。best/runnerUpは全件0.01未満で、猫間の区別条件 .70 を十分に満たす。それでも25件が `outsideRadius` だけで棄却された。

追加の数式上の確認:

- 半径が小さくても下限はない。数値的に0なら `degenerateCalibration`。
- 見本5件中3件の特徴が完全一致すると半径0になり得る。写真のdHash重複検査とは別の条件で、実写真で起きたとは主張しない。
- 登録に用いた特徴でも、他の登録から離れていれば再入力時に棄却され得る。これは中央値・2番目の距離を使うルールの性質であり、直ちに計算バグとは扱わない。

この反例は今回の特徴量を再現したものではない。元の集計だけで原因を一意に特定できないことを示す。

## 4. 次の判断・ユーザー負担

1. 入力失敗、許容半径、猫同士の区別不足を分けることが先。Build 4には既に `inputDiagnostics`、猫別7理由件数、`registrationRadii` があり、最初の切り分けのためにさらに診断機能を増やす必要はない。
2. ただしBuild 4の実行は現在も40枚が必要で、旧選択は復元不可。この制約を隠して再実行を依頼しない。今回は写真再選択を依頼しない。
3. Apple処理との画素比較を行うなら、合成画像だけの限定的なApple実行環境での比較が必要。現状の結果を根拠にCI・配布を繰り返さない。
4. 入力工程だけなら1枚単位の診断で調べられるが、猫個体識別の検証にはならず、現在のアプリにそのモードはない。少数枚診断を導入する場合は目的を入力工程に限定して別途判断する。
5. 半径が主因と分かった場合も、同じ評価写真で閾値を緩めて合格扱いにしない。登録の偏りへの耐性・棄却前候補の正否を診断し、その後に独立標本で検証する。

今回の到達点は、再選択を伴わない構造上の切り分け。実写真25枚の直接原因の確定、識別精度の改善、本番対応完了ではない。

### 確認できたこと

- 同サイズの非対称RGB画像・一定色: nativeと両参照の差0。色順・Float32正規化・行順は一致。
- UIImageの8方向（回転・鏡像）と左上cropの画素確認: absolute tolerance 1e-6で合格。
- 28px拒否/32px採用、座標変換、全体縮小後の128px crop: nativeで確認。
- グラデーション等の低周波画像ではPILとの差のRGB絶対値平均は約0.136〜0.182/255。
- 4px幅で切り替わる帯ではnative対PILのRGB絶対値平均が32.088/255、native対OpenCVが32.138/255。PIL対OpenCVにも17.433/255の差がある。
- 同じnative関数で「原本の256px領域をcrop→224px」と「2048px全体を1024pxへ縮小→128px領域をcrop→224px」を比較。帯模様のRGB絶対値平均差30.627/255。

### 解釈と次の分岐

基本的な色・向き・座標の取り違えは、今回の合成条件では見つからなかった。一方、CoreGraphics `.high` は作者側の処理と画素同一ではなく、細かい模様や縮小順序で大きな差が出た。これは**差の存在の実測**であり、優劣や猫の識別精度への影響を示すものではない。PIL/OpenCV間にも差があるので、作者の推論方式への置換だけで改善するとは言えない。

今回で画像変換の基礎確認は一旦完了。合成テストやTestFlight配布を繰り返しても、失われた旧25枚の保留内訳は分からない。

次の実写真診断を組む場合は、現行の40枚固定UIをそのまま再依頼せず、目的を分離する。

- 入力処理の診断: 選択した1枚について、読み出せたか・猫を検出できたか・cropサイズ・縮小前後の差を確認する。個体を見分けられるかの証明にはしない。
- 個体判定の診断: 見本と猫ラベルのある判定写真が必要。単なる入力1枚診断では代替できない。同じ選択を保持して処理を比較できる形にし、診断写真を独立した合格判定に使わない。

どちらもこのターンでは新しいアプリ機能として追加していない。ユーザーによる写真再選択も依頼していない。実写真から集計するまでは、前処理変更・閾値変更・自動振り分け公開の承認根拠としない。
