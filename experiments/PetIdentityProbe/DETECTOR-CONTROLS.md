## 範囲と受入条件

本線アプリの自動個体振り分けは引き続き保留。本変更は専用検証アプリのみ。

- 明示的な「まとめて確認する」1回で、生成した基準画像3枚と保存済みの猫Aの先頭1枚だけを同じ検出処理に通す。保存した選択を変更・追加しない。未選択なら基準画像だけで実行可能。
- 画像読み出し後の`upright` → Vision revision 2 / `Cat` / confidence 0.5 → 元のcrop条件は変更しない。最大4回の検出。形式fallback、回転比較、別モデル、ONNX、ギャラリー全件検索、ネットワーク取得は行わない。
- 実写真には既存のselected-only / local / current / max1024 PhotoKit取得を使用。画像・ID・検出位置・特徴量をエクスポートしない。選択参照や本線データを変更しない。
- 基準画像は既存のCC0生成素材3枚のみ。専用アプリbundleへ追加し、ライセンス表示に由来を明記。基準画像の候補位置のみ数値で共有・画面に重ねて表示する。実写真用report型は位置情報を持たない。
- 全体は1つのbusy操作。画像ごと・実写真の前後で取消を確認。離脱・background・選択消去後の遅い完了をgenerationで拒否し、画像と結果はメモリから解放する。Visionの同期処理そのものの即時中断は保証しない。
- 読出し失敗、権限失効、検出例外を候補0件と混同しない。写真の権限が失効していても基準画像の結果を保持し、保存した写真はアクセス不可として報告する。

## 分かること・分からないこと

Build 7の本人の1枚は、16bpc/float/extended-sRGBから8bpc/sRGBへ変換してもraw候補0件。形式変換での改善なし。CIの生成対照は2枚成功、1枚で1匹から2候補を返した（詳細は`INPUT-FORMAT-COMPARISON.md`）。

新比較で基準画像が実機でも通るなら、検出器がその実機で常に失敗するわけではないと分かる。本人写真の内容・PhotoKit取得・縮小後の見え方などは未分離。基準画像が通らなくても、OS不具合だけを原因と断定しない。旧30枚のunknown理由や個体識別精度の証明にはしない。

灰色画像の品質条件「見える1匹に対し1候補でcropできる」は未達のまま残す。テストは茶色／白黒の陽性確認と、灰色の既知の制約・安全な棄却の確認に分離する。後者のテスト成功を灰色画像の検出成功と扱わない。共有reportの`allControlsHaveSingleUsableCrop`も、灰色を含む3枚のcropが全て成功しない限りfalseとする。最大候補の無条件採用やbox統合は実装しない。
